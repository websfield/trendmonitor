## Findings

- ❌ BLOCK `respin/packages/db/src/retention-receiver.ts:483-495` with `:438-446` — **The per-row fallback deletes by a ctid claimed in a different, already-committed transaction, so it can delete the wrong row.** On a batch failure the code re-runs `claim()` in its own transaction, which returns `ctid::text` refs under `FOR UPDATE SKIP LOCKED` and then commits, releasing the locks; each ref is then applied in a new transaction as `DELETE FROM ${table} WHERE ctid IN (...)` with no predicate re-check. A ctid is a physical slot, not an identity: an UPDATE between claim and apply moves the row and frees the slot; VACUUM / HOT pruning lets a later INSERT reuse it; VACUUM FULL / CLUSTER relocate everything. Reproduced on PGlite with the fallback's exact statement shape: claim `(0,2)` = the overdue row → unrelated delete + `VACUUM FULL` + one insert → `DELETE ... WHERE ctid IN ('(0,2)')` returned a non-overdue row and left the overdue one in place. A second probe with an ordinary UPDATE showed the milder form: the stale ref matched nothing, the row was silently not counted as poisoned, and `progressed === 0 → break` misdiagnoses the table as "fully poisoned". The batch path is safe (claim and delete share one transaction under row locks); only this fallback is exposed, and the fallback exists precisely for the production wedge the fixtures just found. Every table the sweep DELETEs from is governed retention evidence, and a `session`/`rate_limit` row is updated on ordinary traffic — exactly the claim→apply race. Mechanism: high confidence (reproduced). Production frequency: low-to-medium. · Fix: in the per-row `apply`, delete `WHERE ctid = $ref AND (overduePredicate)` so a reused slot holding a non-overdue row cannot match — or claim-and-apply each row inside one transaction. Then add the missing witness: a DELETE-kind poison (a RESTRICT child planted for one `deletion_operations` row) so the delete fallback runs at all — today `retention-receiver.test.ts:594-642` exercises only the redaction fallback.
