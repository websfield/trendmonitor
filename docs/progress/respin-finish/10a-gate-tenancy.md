## Findings

- ⚠️ CHANGE (Medium) `respin/packages/auth/src/server.ts:65-71` — The new "ONE CLIENT-IP AUTHORITY" docstring claims `null` when no trusted proxy resolved an address, "never a guess from an untrusted header"; `respin/packages/db/src/public-sample-spin.ts:17-19` and the allowlist rationale at `respin/tests/gate-completeness.test.ts:96` ("one admission per 24 h") inherit that claim. It is false under `RESPIN_TRUSTED_PROXIES=none`, a supported production value (`create-auth.ts:40,247` returns `undefined`): the installed `@better-auth/core@1.6.28` `getIPFromHeader` (`node_modules/.pnpm-copy/@better-auth+core@1.6.28.../dist/utils/ip.mjs`) trusts a **single-value** client-supplied `x-forwarded-for` when `trustedProxies` is empty (`if (forwardedIps.length !== 1) return null; … return normalizeIP(selectedIp)`), and the auth suite already relies on exactly that shape (`packages/auth/tests/rate-limit.test.ts:34-38`). On a directly exposed deployment a visitor mints a fresh HMAC bucket per request by setting the header; only the $10/day cap and the 2-concurrent limit remain. No test in the diff calls the real `canonicalClientIp` (`tests/demo-route.test.ts:13` mocks it). PII posture is unaffected (still only an HMAC lands) — this is a T8 comment-is-not-a-property finding with an abuse-boundary consequence the billing reviewer should weigh. · Fix: add a test that drives `canonicalClientIp` under `none` with a client-supplied single-value `x-forwarded-for`, and either rewrite the docstring to say what Better Auth does or have the Sample Spin treat `trustedProxies === undefined` as `NO_TRUSTED_IP` (shared bucket, fail closed) so the promise holds.
- ⚠️ CHANGE (Medium) `respin/packages/db/src/creator-data-registry.ts:458` and `:464` — The two new `public_sample_spin_row` / `linkable_source_ids` rows (`system_model_usage`, `system_spend_claims`) claim `retention: operational_90_days, executor: identifier_scrubber`. Nothing can ever run that: the scrubber's predicate for these rows is `snapshot_indirect` against a *creator's* source ids (probe output: `predicate=snapshot_indirect executorMatchesPublicRow=false` for profile and workspace ops), a visitor has no erasure path, and `assertRetentionClockClosure` exempts non-receiver executors (`retention-clocks.ts`: `if (!isReceiverExecutor(entry.executor)) continue;`) so the closure stays green. Executed: after `runRetentionTick` at +91 days both `job_id`s were intact (`claims job_id after 91d: 1111…,2222… | usage job_id: 1111…,2222…`). Consequence: the visitor's browser-random request id sits with the 7-year cost facts, while `/legal` (`app/(marketing)/legal/page.tsx:27`) says the Sample Spin records "only the cost of the model calls and a keyed hash of your connection address for twenty-four hours". The id is unlinkable to a person once the bucket expires (neither claim nor usage references the bucket), so severity is Medium, confidence high on the fact. The autopsy `system_row` carries the same dead 90-day rule from 10b-1, but this is the first class where it is unrunnable by construction. · Fix: register these ids honestly under the financial chain (7 years, content-free, which is what R-122 already says for `public_sample_spin` facts) and remove the 90-day claim — or add a receiver measure that can actually run, using `random_token` redaction as `stripe_customer_id` does, since `job_attempt_id` is NOT NULL/unique and is the claim↔usage link and cannot be nulled.
