## Findings (new)

- ⚠️ CHANGE `respin/packages/db/src/deletion-lifecycle.ts:2652-2655` — The reopen decision reads the period-end row's status at cancellation time, but the executor dispatches that fence **outside any workspace lock** (`deletion-executor.ts:353` → `deletion-external-commands.ts:419-436`: `markDispatched` commits, then the Stripe call, then `recordExternalCommandOutcome`). If the owner cancels during that provider round-trip, cancellation sees `pending` (dispatched, unresolved), enqueues no reopen, commits `cancelled`; the fence then lands `cancel_at_period_end: true` and is recorded `succeeded` — the exact round-1 BLOCK-2 consequence (workspace active locally, paid subscription silently ends at period end, no reopen ever), now narrowed to one round-trip per operation. Confidence high on the mechanism; the window is real because `latestExternalCommandInTx`'s `FOR UPDATE` only serialises against the outcome write, not against the in-flight provider call. · Fix: treat a pre-grace row with `status = 'pending' AND dispatched_at IS NOT NULL` as in-flight and refuse cancellation on it exactly as on `unknown` (extend `assertNoUnknownExternalCommands`), or enqueue the reopen for `succeeded OR dispatched-pending` (a row's existence already means "ours", and the reopen dispatches on a later tick after the fence outcome is recorded); pin with a test that marks the row dispatched before cancelling.

- ⚠️ CHANGE `respin/packages/db/src/deletion-executor.ts:135-145` — The financial-chain gate is scoped to `workspace` and to three tables, but R-122's first bullet also names "model-usage … facts" (`docs/initial/decisions.md:1640`), and `model_usage` — tokens, `cost_micro_usd`, `config_version`, `stripe_price_id`, the REQ-G05 margin input (`packages/db/src/onboarding-schema.ts:317-347`) — is registered as a **profile-scope cascade under `profile_lifetime`** (`creator-data-registry.ts:312`, FK cascade `:714`). Profile erasure is not held by the gate, the worker accepts `profile` at startup, and the populated fixture never inserts a `model_usage` row (grep: 0 occurrences in `deletion-executor.test.ts`) although plan C3 lists "model usage/ledger/spend rollup" in the mandatory population (`docs/plans/respin-finish-phase-10b-1.md:99`). So once Task 5's journal lands, a profile deletion destroys seven-year cost facts with no witness. This is my own round-1 list being incomplete, stated as such. · Fix: either add `model_usage` to the chain list with a profile-scope predicate in `unretainedFinancialChainTables`, or re-register it like `system_model_usage` (pseudonymise `profile_id`/`attempt_id`, `retain_financial` the cost columns); populate the fixture and assert cost survives and the link does not. `first_billable_attempts` is an entitlement marker, not a financial fact — leaving it cascading is defensible.

- ⚠️ CHANGE `respin/packages/db/src/deletion-executor.ts:479-482, 539-545` — Hunt (g). The orphaned journal version is recorded as "the S3 adapter's conflict rule must be designed for it", but plan C2/C4 fix that rule: conditional create, "existing version objects are never overwritten", "any gap/conflict blocks" (`respin-finish-phase-10b-1.md:87, 103`). Under that rule a rolled-back erasure leaves `N = verifying` in S3 with the DB at `N-1`; the next `blocked` append at `N` gets a conflict, `handleErasing` rethrows, and every later tick repeats verifying-at-N → conflict → blocked-at-N → conflict. The operation is wedged in `erasing` after `stripe_subscription_cancel_now` and the customer clear have already run — it can neither complete nor be cancelled. The in-memory port accepts the second append, so the round-1 lean C1 witness (`deletion-executor.test.ts:676-733`, pinned at `:722-732`) proves resume only for a port production will not use. Not a money BLOCK: no charge or refund moves and production erasure is off until Task 5. But the placement is not honest — the adapter cannot fix this without violating C4; the executor must stop reusing a version number. · Fix: commit the `verifying` transition durably (DB + journal) in its own transaction before the effects run, so the erasure transaction operates under `verifying` and a residue rollback goes `verifying → blocked` at `N+1`; re-word the stated limitation as a Task-4 executor item.
