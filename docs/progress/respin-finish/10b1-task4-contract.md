## Design decisions the reviewers should weigh

1. Stub-and-repoint receipts. The deletion projection tables carry RESTRICT foreign keys to `users`, `workspaces` and `creator_profiles` and CHECKs that forbid a null target, so a completed receipt cannot simply lose its link. Erasure creates a random stub root (`Deleted member` / `Deleted workspace` / `Deleted profile`, tombstoned, mapping discarded) inside the erasure transaction, repoints every retained link at it, then deletes the real root. This is R-122's "irreversibly pseudonymised receipt" made structural; the alternative of loosening the CHECKs was rejected.
2. The transitions composite FK is now DEFERRABLE INITIALLY IMMEDIATE (0052) so parent and child can be rewritten together; the erasure transaction issues `SET CONSTRAINTS ... DEFERRED`.
3. Partial `delete_explicit` field sets are retention clocks (receipt facts one year, provider payloads 90 days, recovery secret seven days) and are skipped at subject erasure by executor and probe alike; Task 6's receiver owns them.
4. The executor scrubs `requester_digest` (an unkeyed sha256 of the user id, outside the registry's declared linkable set) on identity erasure, per operation, because a known-id dictionary would otherwise relink the retained receipt.
5. For identity operations no Stripe customer clearing runs: the billing-contact binding (plan C3) does not exist until the later tasks; workspace erasure clears the workspace customer.

## Stated limitations (not defects hidden as done)

- Better Auth runs `sendResetPassword` through its background-task helper and answers the generic "check your email" reply regardless of the hook's outcome (its enumeration guard). The outbox row is the durable truth; the reset page copy in Task 8 must not claim delivery.
- For password reset the challenge store remains Better Auth's `verification` row (token value, not a digest), already lifecycle-covered by the 24-hour receiver and identity erasure. Email verification is a signed JWT with no row.
- The Stripe customer-clearing call uses the installed SDK's `Emptyable` contract (`''` empties a field); a live proof against a real account is separate rollout evidence, as is real Resend delivery (T-16).
- The `pgboss.*` supporting stores are erased/probed only when the physical `respin_worker` schema exists; PGlite fixtures have none. The real-Postgres pg-boss suite does not yet drive an erasure across a populated job table.
- Production composes `unavailableDeletionJournal` until Task 5's S3 store lands: every append refuses, so no operation can advance; the executor tick runs and reports counts only.
- Runtime tightening of the mail ceilings has no config document key yet; the authority accepts an override and refuses one that erodes the compiled security reserve (20/day, 600/month), and the compiled ceilings apply until 10b-2 wires one.
- **Journal receipts and effects commit together (round 2 closed a round-1 limitation).** The first fix appended `verifying` to the journal before the executors ran, so a rolled-back erasure left an orphaned version N in the journal and the next append (`blocked`) reused N with different content — a conflict under R-124's conditional-create, never-overwrite store, which would have wedged every residue-blocked operation in production (round-2 billing CHANGE 3, tenancy CHANGE 3, lean C-R2-2). Both receipts (`verifying`, `complete`) are now appended AFTER the executors and the independent probes, inside the same transaction: a rollback appends nothing, no version is ever reused, and the effects still become visible only at commit, after both appends were durably confirmed. Pinned in the residue test (every journal version appended exactly once, in order).
- **A rolled-back erasure is retried three times, then waits for an operator.** `DELETION_EXECUTOR_MAX_ERASURE_FAILURES`; `retry_count` carries the count and the blocked path refuses to resume an exhausted operation (`blocked_awaiting_operator:erasure_failures_exhausted`) until an operator resets it (round-2 lean C-R2-1). The runbook names the procedure; the admin surface for it is Task 8's.
- **Every scope's irreversible erasure is held today, by the executor's own derivation (`erasureHold`).** Workspace and profile while the financial chain still cascades (`credit_ledger`, `subscriptions`, `pause_periods` at workspace scope; `model_usage` at profile scope — R-122 "model-usage … facts", round-2 billing CHANGE 2); identity while the raw Stripe payload that names a workspace's contact has no receiver (`STRIPE_PAYLOAD_RECEIVER_WIRED = false`, round-2 lean S-R2-1). The worker refuses any scope token with the same reason at startup. Task 6 lifts all three in the change that wires the receivers. The three populated walks take the grace→erasing step by hand after pinning the hold, so what erasure DOES is still proven end to end.
- **Cancellation does not re-arm auto-top-up.** Plan C2 reverses only the listed reversible controls; re-arming is the owner's reauthenticated choice. Task 8's cancellation copy must say so.
- **The raw Stripe payload survives subject erasure** (`stripe_events.payload`, `delete_explicit` under `stripe_payload_90_days`): it is Task 6's finance-extract input and is purged by Task 6's receiver. A completed workspace erasure — and an identity erasure of the workspace's Stripe contact (round-2 lean S-R2-1) — would therefore still hold that email in the column for up to 90 days, which is why every scope's erasure is held until Task 6 (previous bullet). Pinned in the workspace walk and the identity walk.
- **Reachability of the 90-day mail receiver.** `sweepExpiredAuthMail` exists and is tested but nothing in the worker calls it yet; Task 6 wires the retention receivers. It is inventory, not a live capability (Definition of Done, reachability).
- **`env.example` gap, corrected.** The first version of this contract claimed `env.example` documented `RESPIN_DELETION_ERASURE_SCOPES`; it did not until the round-1 fix pass added the block. Recorded as a Golden-rule-1 miss (a claim recorded without re-reading the file it names).
