## Findings

- ❌ BLOCK `respin/packages/credits/src/stripe/deletion-commands.ts:131-134` — The `auto_topup_disable` fence sets only `autoTopupEnabled = false`, the **legacy** flag. The schema calls `autoTopupV1Enabled` the "Sole charge authority for the durable protocol" (`packages/db/src/billing-schema.ts:152-158`), the charge gate reads only that flag (`packages/credits/src/stripe/auto-topup.ts:445`), and every existing disable site clears four fields — `autoTopupEnabled`, `autoTopupV1Enabled`, `autoTopupRearmAfterUpgrade`, `autoTopupMonthlyCapCents` (`actions.ts:1413-1416`; `webhooks.ts:254-257` `DEAD_SUBSCRIPTION_FIELDS`). Worse, the executor enqueues the fence only `if (subscription?.autoTopupEnabled)` (`packages/db/src/deletion-executor.ts:173`), and under the active protocol "the legacy bit stays false forever" (`actions.ts:1411-1413`) — so for every v1-armed workspace the fence is never enqueued at all, the reconciler (`deletion-commands.ts:203`) would still report `succeeded`, and the rollout activator can re-arm v1 from the uncleared `autoTopupRearmAfterUpgrade` (`auto-topup-rollout.ts:519`). A tombstoned workspace can be charged a $10 pack off-session through grace. The test is a witness-absent case: the fixture seeds `autoTopupEnabled: true` (`packages/db/tests/deletion-executor.test.ts:284-291`), a state production cannot hold under v1, and `deletion-commands.test.ts:117-124` asserts only the legacy flag. · Fix: enqueue when any of the four charge fields is armed; set all four exactly as `DEAD_SUBSCRIPTION_FIELDS` does (and clear an undispatched pending attempt as `actions.ts:1360-1376` does); reconcile on `autoTopupV1Enabled`; seed the fixture v1-armed (`autoTopupV1Enabled: true, autoTopupProtocolVersion: 1, autoTopupAttemptCutoverAt`) and assert the v1 flag is false after the fence.

- ❌ BLOCK `respin/packages/db/src/deletion-lifecycle.ts:2565-2635` — The cancellation phase is declared but not wired. `applyScopedCancellationInTx` appends `cancelled` and flips the workspace back to `active`; it never reads `deletion_external_commands` (the file's only command read is the grace/erasing gate at `:3377-3381`), so an `unknown` pre-grace outcome does not block cancellation as plan C2 and manifest line 33 claim. `stripe_subscription_reopen` is enqueued nowhere (grep: only the enum, `EXTERNAL_COMMAND_PHASE_BY_KIND`, the adapter and tests), and the executor's `DUE_STATES` excludes `cancelled` (`deletion-executor.ts:72-78`), so a cancellation-phase row could never dispatch anyway. Money consequence: owner requests workspace deletion → Stripe receives `cancel_at_period_end: true` (`deletion-commands.ts:140-144`) → owner cancels inside grace → workspace is `active` locally while the paid subscription still ends at period end, silently; auto-top-up stays off silently too. Plan C2 workspace row: "clear a still-pending period-end cancellation before reopening". Note the executor correctly skips the pre-grace command when the owner had already scheduled their own period-end cancellation (`deletion-executor.ts:170`), so the reopen must be conditional on a **succeeded** `stripe_subscription_cancel_at_period_end` row of this operation, never unconditional — otherwise the fix resurrects a subscription the owner ended. · Fix: in `applyScopedCancellationInTx` under the workspace lock, call `assertNoUnknownExternalCommands`, enqueue `stripe_subscription_reopen` iff this operation's period-end command succeeded, dispatch cancellation-phase rows (add `cancelled`-with-pending-commands to the due set or dispatch inline), and test the round-trip with the fake port, including the pre-scheduled-cancellation fixture.

- ⚠️ CHANGE `respin/packages/db/src/auth-mail.ts:95-110` — The tighten-only override can erase the security reserve. Executed against the installed function: `resolveAuthMailCeilings({ totalPerDay: 60, totalPerMonth: 1800 })` → `{ invitesPerDay: 60, invitesPerMonth: 1800 }`, effective reserve **0/0**. R-118 (`docs/initial/decisions.md:1604`) requires "at least 20/day and 600/month"; the code's own comment at `:72-76` says "nobody can configure it away". `auth-mail.test.ts:132` only covers total < invites. · Fix: enforce `resolved.invitesPerDay <= resolved.totalPerDay - AUTH_MAIL_SECURITY_RESERVE.perDay` (and month), either refusing or auto-tightening invites; add the `{ totalPerDay: 60 }` case to the test.

The registry states honestly that `credit_ledger`, `pause_periods` and `subscriptions` still cascade with the workspace under `workspace_lifetime` (`creator-data-registry.ts:292-298`), and the executor test pins `creditLedger` empty after erasure (`deletion-executor.test.ts:400`) — contradicting R-122's seven-year financial chain and plan C3.
