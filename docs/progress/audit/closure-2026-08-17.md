**Read the Proof column carefully.** It distinguishes three kinds of claim, and
the audit's own rule (and the plan's stop condition) is that they never blur:

- **ENG** — engineering proof: code plus a test that fails without it.
- **CI** — proven by a check that runs in CI on every PR.
- **OWNER** — needs a person, a credential, or a deployment that does not exist
  yet. **Never marked closed.**

### The review's own two fixes went through the Critical-Path gates, and both failed the first time

Stated plainly because it is the more useful record: the two fixes above were
gated by `respin-billing-reviewer` and `respin-tenancy-reviewer`, both returned
**NEEDS CHANGES**, and both caught in this review's work the *same defect class
this review had just criticised in the remediation*.

**Billing — the first fix was wrong in the direction that costs money.** Gating
the pack charge on the subscription *mirror* left `{open pause_periods, mirror
canceled}` permitting a purchase whose credits `debitCredits` refuses to spend,
with no way to close the pause. Worse than the bug it replaced: the original
blocked a sale, the fix would have taken money for nothing. The guard now
refuses if **either** record says paused, which makes the sell-side refusal a
strict superset of the spend-side one — the property that makes unspendable
credits unrepresentable. Two new cases drive the charge and the spend against the
same row; mutation-proven red. **Round 2: PASS (A).**

The re-gate also established something the fix's own comment had got wrong:
every writer of `subscriptions.pausedAt` lives in `pause.ts` and writes the
period and the mirror as a transactional pair, so `pausedAt set ⟹ open period`
holds at every commit boundary. The mirror half is therefore defence-in-depth
against a divergence the writers prevent — not a second live hazard. The comment
now says that, instead of justifying the half with a row shape nothing can
produce.

**Tenancy — the guard claimed more than it enforced, twice.** Round 1: the IP
validator admitted ten values Better Auth silently drops, every one of which
returns all tenants to the single shared sign-in bucket the guard exists to
prevent; the environment gate exempted `staging` and an unset `NODE_ENV`, which
get no localhost fallback and had the limiter on; and R-27 claimed the hazard was
"reproduced empirically" when a `NODE_ENV=test` process cannot reach production's
code path at all. Round 2, after those were fixed: **nine more over-accepts**, in
classes the round-1 fix had not touched — zero-padded IPv4 (`010.000.000.000/8`,
which a person would plausibly type) and IPv6 group-count errors — one of which
the reviewer drove end-to-end to `no-trusted-ip`, the outage, from a value the
guard accepted.

That second round is the entry worth keeping: the round-1 test pinned **18
hand-picked strings**, the validator was fixed until those 18 passed, and the
class stayed open. It is this repo's 2026-07-30 lesson in its failing form —
*fix the class, not the named instances; "grep every sibling id" is the version
of this rule that already failed once*. The validator is now structurally strict
(no leading-zero octets, exact IPv6 group counts) and the direction test is
**generative** — a permutation corpus of 300+ strings, mutation-proven to catch
the padding class the list missed.

**Verdicts: billing PASS (A) at round 2; tenancy PASS-equivalent at round 3** —
its final CHANGE was a missing paragraph, not a code defect, and it is now
recorded (see below). The round-3 reviewer closed the validator class against an
**independent 331,586-case fuzz it built itself** — 0 direction violations, 609
values accepted, all 14 previously-known over-accepts refused, and every
real-world anchor still accepted, including a two-hop chain resolving its true
client.

**A third self-inflicted finding, and the most instructive one.** In asking for
that re-gate this review *told the reviewer it had recorded* the inherent
residual limitation in R-27. It had not — only the validator claim had been
corrected. The reviewer read R-27 end to end, grepped it, and said so. Recording
a thing and reporting it recorded are different acts, and this review conflated
them while auditing a remediation for exactly that. The paragraph now exists:
the validation bounds the *syntactic* class only, a well-formed but semantically
over-broad range (`0.0.0.0/1`, or any range containing real clients) still
resolves no client and reproduces the shared bucket, no construction-time probe
can decide it without knowing which clients arrive, and the mitigations are
operational — narrowest-covering ranges, plus Better Auth's one-time
"could not determine a client IP" warning as the only runtime tell. Every claim in R-27 that outran the
code was corrected rather than defended: "refuses to boot" → fails every auth
request from the first one (the process starts, static pages render, so a deploy
can go green with the failure latent); "reproduced empirically" → the
*consequence* is demonstrated end-to-end, the *mechanism* is read from the
installed package.

**One finding neither gate raised and this review created:** declaring
`@better-auth/core` a dependency of `packages/auth` made pnpm materialise a
second copy of it, so the validator would have measured itself against a
different instance than the runtime uses. Reverted; the test resolves the real

**A last round on the lock, and it found the retraction had not fully landed.**
Adding `takeWorkspaceLock` to `pauseSubscription`/`resumeSubscription` closed the
gate's own NOTE, and the gate confirmed all three properties it was asked about —
no deadlock (one advisory lock keyed per workspace, taken before any write in
every transaction that takes it), no network call inside a held lock, and no
change to the convergent pause semantics or the round-10 symmetry bound. It also
noted the lock is placed *before* `getDbNow` for a reason worth keeping: reading
the clock first would let a contended wait produce a `ClockSkewError` on an
ordinary pause.

But it caught the `packAmountCents` retraction living in only **one of its three
copies** — the call-site comment was corrected while the helper docblock and,
worse, the **operator-facing warn message** still asserted the two "cannot
disagree". The log line is read exactly once, by a human, at the moment the
branch fires — which is precisely when an `/admin/config` edit may have voided
the claim. All three now agree, and the warn tells the operator what to compare.
The lock is pinned by a source guard that asserts it is taken **first** — not
merely present — because placement is load-bearing twice over (before `getDbNow`,
or a contended wait can throw `ClockSkewError` on an ordinary pause; and before
any write, which is what rules out an advisory-vs-row-lock cycle). Both
assertions are mutation-proven, and the guard is explicitly labelled
for what it does not prove (presence, not serialization — the behavioural proof
needs two connections, and mocking Stripe inside the one suite that proves the
