- 2026-08-20 — **M2a gated (round 1): tenancy BLOCK (4), billing BLOCK (4).** Both reviewers verified by execution rather than reading, and both independently reached the same conclusion about the pause predicate.

  **The design premise was false, and two gates found it separately.** A-7 injected the pause predicate because `packages/db` supposedly could not reach `hasOpenPause` without a cycle. But **`pause_periods` is defined at `packages/db/src/billing-schema.ts:263` — `packages/db` owns the table.** The predicate is a six-line select and simply moves there. The injection design bought a caller-side hole the graph never required (`isPaused` is structurally typed, so `async () => false` satisfies it, and the AC could only ever test the plumbing with a stub) and had **no wiring layer that could supply it**: the sole production mint is `packages/db/src/app-server.ts:27`, inside the package that must not import credits. Moving the predicate collapsed four findings at once, including a duplicate `WorkspacePausedError` that would have failed `instanceof` against the real one and rendered a pause refusal as "Something went wrong".

  **`#private` defeated one of the three forges, not three.** The tenancy gate recompiled against the class shape with the repo's `typescript@5.9.3`: **five routes reached `writeCapabilities` at exit 0** — `Object.assign` (its declared return type is an intersection satisfying `#cage` while the runtime value has no private field), `{} as ProfileScope`, a subclass, a `Proxy`, and `new ProfileScope(...)` because the constructor was public. It then measured the runtime matrix: `#cage in x` **accepts a subclass**, `instanceof` accepts subclass and Proxy, and **only a module-private `WeakSet` rejects all three**. Fix taken: `private constructor` + `static mint` (TS2675/TS2673, verified) **and** the `WeakSet` asserted in `writeCapabilities` — complementary, not alternatives.

  **Three more that were probed, not argued.** The eslint allowlist grants a class as a **value** — four fixtures run through the installed ESLint showed value-import and `extends` both ALLOWED, since `allowImportNames` makes no type/value distinction (fix: export the scopes as types only). `createProfile` reproduced the exact hole A-2 closed, one level up — on the instance `app/**` legitimately holds, with a caller-supplied cap and **no role check, so a viewer could create profiles** (REQ-A02).   **Three things building surfaced that six rounds of plan review could not.**

  1. **drizzle-kit 0.31.10 cannot serialize a BigInt default.** `.default(0n)` typechecks and then throws `TypeError: Do not know how to serialize a BigInt` inside `db:generate`. A bigint default must be written as `sql\`0\``.

  2. **A composite FK cannot reference a `uniqueIndex` in a drizzle-generated migration** — an ordering trap, not a syntax one. drizzle-kit emits every `CREATE TABLE`, then every FK `ALTER TABLE`, then every `CREATE INDEX`, so the index does not exist when the FK is added: `there is no unique constraint matching given keys for referenced table "creator_profiles"`. The fix is a table-level `unique()` **constraint**, which is emitted inline in `CREATE TABLE`. **The plan's own migration step said to inspect the emitted SQL for four things Drizzle may not produce — the constraint was PRESENT and the check passed; it was present too LATE.** "Verify it is emitted" and "verify it is emitted in a working order" are different checks.

  3. **`drizzle-kit migrate` exits 1 on failure and prints no reason.** The spinner clears the line and the error never reaches the operator — all that is visible is `applying migrations...`. It reports correctly when there is nothing pending, so the failure is invisible exactly when something is wrong. The real error came out immediately from `drizzle-orm`'s own programmatic `migrate()`.

  **And why none of that was caught before:** `db:check` works **offline**, comparing schema against migration files with no database. So the entry gate has always been green while **nothing in it ever verifies that migrations apply**. The local dev database was two migrations behind at 0009 — missing `rate_limit`, from the audit's own auth-hardening work. Two pre-existing findings for the owner: the migrate runner swallows errors, and CI never exercises migration application.

  **A process note, recorded because it is the kind of thing that should not be silent.** While diagnosing, I applied `0010` directly via `psql` to surface the error, which created `rate_limit` outside drizzle's journal. That was the wrong order — diagnose first, mutate never. A subsequent `DROP TABLE` was correctly refused by the safety layer, so the state was reported to the owner rather than quietly reconciled; on the owner's decision the empty table was dropped and both migrations re-applied through the sanctioned migrator, leaving the journal truthful.
