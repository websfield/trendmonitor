## A11Y-1 — reading order and visual order disagree in the mobile product nav (open)

**Found by measuring, on 2026-09-20, the first time the probe's worry was turned into a check.** `e2e/visual/visual.spec.ts` now reads the product nav's accessibility-tree order (DOM order, with `aria-owns` and role-bearing `display: contents` asserted absent so the premise holds) and compares it with visual top-to-bottom order. At 390 and 799 with the drawer open, on all three engines:

- **tree:** More · Studio References Brain Results · Onboarding Usage Billing Account · Colour Pop After Hours · Sign out
- **visual:** More · Onboarding Usage Billing Account · Colour Pop After Hours · Sign out · Studio References Brain Results

The four primary links are the fixed bottom bar at mobile, so a sighted user meets them **last** and a reader traverses them **first**. A reader who activates "More" then walks all four before reaching the drawer that opened visually right above the control they pressed — five Tab presses, pinned in the test so shortening it is deliberate and lengthening it is a regression. On desktop (1024) the two orders agree, and that contrast case is asserted too, so the mobile expectation cannot be satisfied by a shell whose orders never agree anywhere.

**Deliberately not fixed here, and deliberately not blessed.** Not fixed: reordering the mobile shell changes the layout the 93.3% design score was awarded on, and no reviewer has seen this finding. Not blessed: both orders are asserted explicitly rather than one being pinned and called a pass, and the failure messages name the divergence. **WCAG 1.3.2** is the criterion.

**Ruled 2026-09-21 — accepted as known (decisions.md R-133).** The owner accepts the divergence rather than reordering the mobile shell, which would change the layout the 93.3% design score was awarded on. Accepted is not fixed and not blessed: the two-sided assertion in `e2e/visual/visual.spec.ts` stays, the five-Tab distance stays pinned, and the failure messages still name the divergence, so any future shell change forces a deliberate re-ruling. No conformance claim is made for this surface.

**Engine coverage, stated exactly.** The tree-vs-visual comparison runs on Chromium, Firefox and WebKit. The Tab-distance assertion runs on Chromium and Firefox only: WebKit's default keyboard mode moves Tab focus to no anchor at all (measured — it returns `[Colour Pop, After Hours, Sign out, "", Save fixture draft]`), which is Safari's "press Tab to highlight each item" default inherited by Playwright's WebKit, not a defect in the drawer. WebKit there asserts only that the drawer's first button is reached. WebKit automation does not certify Safari hardware either way.

**One incidental correction the same work forced.** The first draft asserted `aria-expanded` as an attribute on `<summary>` and read `null` on all three engines: `<details>`/`<summary>` expose expanded state **implicitly**, computed into the accessibility tree from `details.open`, and never write the attribute. Hard-coding one would put a hand-maintained value beside the implicit one and let the two disagree, so `details.open` is what is asserted and the implicit exposure is named as the part only a real reader can confirm.
