## Objective

One tenant's Stripe degradation can fail every tenant's pages. The webhook dispatcher takes the per-workspace billing lock and handlers then call Stripe under it, with a pinned worst case of 250 s per call — so one `invoice.paid` can hold a workspace's lock for roughly 750 s. Meanwhile **every product page render folds the balance** (`layout.tsx:31-33` → `balance.ts:62`, which takes the same lock) and `/studio` folds again (`studio/page.tsx:258-262`), each blocked render holding one of ten pooled connections, with no `lock_timeout` anywhere. `balance.ts:57-60`'s own comment already names this: "waiting for the lock IS part of what a caller experiences, and it is the contention D-M1-7 says will bite first."

The register's fix has three parts. **This phase takes the two that decouple the tenants** — a non-blocking read on the display path and a bounded wait on render transactions — and records the third (moving Stripe mutations out from under the lock, via the outbox 10b-1 already built) as a decision with a trigger. Rebuilding the money path's transaction boundaries to fix a display-path coupling is the larger risk, and the coupling is gone without it.

The phase also closes the asymmetry between the two model call sites: the public, unauthenticated one is on the weaker pattern.

**Lesson that bites here (generalist pre-mortem):** a Postgres `SET lock_timeout` without `LOCAL` persists on the pooled connection, so the next webhook or debit transaction on that connection would abort at 5 s with a lock error the money path was never designed to receive. The helper issues `SET LOCAL`, and a test proves the next transaction on the same connection reads the default.

## Edge cases and external failures

| Condition | Handling | Requirement |
|---|---|---|
| The non-blocking read returns a stale balance right after a purchase | The page renders the committed fold and says the number is settling; it never renders a *wrong* number as final, and the write path is unchanged | P8-R1 |
| `lock_timeout` fires on a legitimate slow write path | It cannot: the setting is `SET LOCAL` inside `withRenderTransaction` only, and the money path's own transactions never call that helper (row 10's scan). The card names every transaction it applies to | P8-R1 |
| `SET lock_timeout` without `LOCAL` leaks to the next money transaction on the pooled connection | Refused by construction (`SET LOCAL`) and by row 10's leak test, which plants the bare `SET` and reads the next transaction's `lock_timeout` | P8-R1 |
| The committed fold has no source on a workspace whose free mint is due but not yet minted | The fallback folds committed rows only and skips both under-lock writes (the mint and the expiry materialisation); the number is rendered as settling and the next unlocked render mints. It is never rendered as unavailable for contention alone — unavailable (`null`) stays reserved for `LedgerIntegrityError` and access refusals | P8-R1 |
| A `pause_periods` row commits between the rows read and the pauses read | It cannot shift the fold: both sets come back from **one statement**, so `effectiveExpiresAt` is computed against one instant — no isolation-level change, which the transaction could not make after `SET LOCAL` anyway | P8-R1 |
| `lock_timeout` fires inside the derive after the try-lock succeeded | `getDisplayBalance` catches `55P03` from that branch and renders the committed fold, settling — the same fallback as a failed try-lock; never `null`, never a hang | P8-R1 |
| A screen decides "insufficient" from a settling number | Refused: `run-copy.ts` makes no comparison; insufficiency is decided at the two `generate.ts` sites on the money path's own `deriveBalance` read — the pre-call gate (`:567-618`) and `settle`'s debit — and AC1 renders a settling balance below the cost without a refusal sentence | P8-R1 |
| The mirror (`subscriptions.pausedAt`) and the authority (`pause_periods`) disagree at the instant a page folds | The fallback reads the authority alone (`loadHistory`), so the fold and `studio/page.tsx:186`'s `paused` flag agree with each other whichever way the two truths disagree; AC10 plants both directions. Collapsing the two truths is not this phase's — the master's deferral ledger keeps it with its trigger, and this phase's card records only which truth the new consumer reads | P8-R1 |
| A new bundle digest invalidates cached generations | That is REQ-J02 working. The two digests are recorded in the card, before and after | P8-R2 |
| Escaping `context.input` changes model output quality | Possible, and the honest answer is that a delimiter and an untrusted-material clause are what the autopsy path already runs with. The card records one before/after generation on the same fixture | P8-R2 |
| Two callers create the Stripe customer concurrently | Stripe answers the in-flight duplicate with `409 idempotency_key_in_use`; the loser retries once and receives the winner's customer; the mapping race then converges on one id (P8-R5) | P8-R5 |
| The mapping insert fails after Stripe returned the customer, and the retry lands after 24 h | The key has expired, a second customer is created, and the existing orphan path names it by `metadata.workspace_id` — reconcilable, never silent | P8-R5 |
| The mapping insert fails, and the creator changes the billing email before retrying inside 24 h | The email hash is part of the key, so the retry is a new key: a second customer is created and mapped, the first is an orphan findable by `metadata.workspace_id`; without the hash Stripe would answer `400 idempotency_error` for the rest of the window and no checkout could proceed | P8-R5 |

## Reachability

A creator whose workspace lock is held by a slow `invoice.paid` handler still gets every product page to render, with a committed credit number marked as settling (`app/(product)/layout.tsx` and `shell-rail.tsx`, rows 5–6, on every `(product)` route; the four page-level readers, rows 7 and 9 — all five through the facade binding at row 20); a stranger's injection specimen through `POST /api/demo` (`app/api/demo/route.ts`) and a creator's through `/studio` meet a delimited, untrusted-marked prompt (row 11); a creator's first billing action creates one Stripe customer under a durable key (row 16, on the existing checkout path). ## Least confident

Whether the committed-fold fallback is always cheap and always present. It folds committed rows only and skips the under-lock mint and materialisation, so it needs no new column — and the batch-0 gate's riders are now structural claims with witnesses (AC8: `foldLedger` only, one snapshot, the settling metric). What remains uncertain is cost: a large ledger folded on every render without the lock is the same work `getBalance` already does, so no worse, but it is done on a contended connection. If a fold without the lock ever renders a wrong-as-final number, the phase renders the settling indication with **no** number rather than a wrong one. The card records which. An unstated number is honest; a wrong one and a blocked page are not.
