## Decisions baked in (defaults the doc set doesn't settle)

| # | Decision | Default chosen | Why / revisit | Recorded |
|---|---|---|---|---|
| D-M1-1 | Webhook idempotency state | Dedicated `stripe_events` table (Stripe event id as PK, type, `workspace_id` nullable FK + `stripe_customer_id` resolved at receipt, received/processed timestamps), **plus** the ledger's unique `stripe_event_id` column as defense-in-depth (tech-spec §2). **Transactional design (billing round-1 finding 1):** the event-row insert, the handler's writes, and the processed-mark commit in **one transaction** — a failed handler rolls the event row back too, so no stale in-flight row can exist; a concurrent duplicate blocks on the PK then conflicts after commit (→ 200), and an existing row therefore always means processed (→ 200). Never an early-200 on in-flight work; a handler error yields non-2xx so Stripe redelivers. | Not every event writes a ledger row (e.g. `subscription.updated`), so ledger-only idempotency can't cover them. Revisit: never on principle; unattributable-event retention sweep is a named M6 receiver (Deferral Ledger). | Append as R-20 (Phase 1 task) |
| D-M1-2 | Config v1 versioning shape | Append-only `config_versions` rows (serial `version`, `content jsonb`, author); active = max version; content Zod-validated by `packages/config` | Mirrors the brain_docs append-only pattern and R-6 "versioned DB config". | D-M1-3 | "Credits frozen / expiry clocks suspended" representation | Ledger rows stay **immutable**; `pause_periods` holds one row per pause period (workspace, started_at, ended_at — **close-on-resume by setting `ended_at` is its single sanctioned update; it is not append-only**, and no other column is ever rewritten); the balance authority computes **effective expiry** = `expires_at` shifted by pause overlap (chronological fold) | Preserves B1 strictly for the ledger — no UPDATE to ledger rows ever; pause history stays auditable. Revisit: if derivation complexity/cost bites, supersede with shift-on-resume UPDATE + audit row, by decision entry. | R-20 |
| D-M1-4 | No background job runner at M1 | Grace/downgrade state is **derived lazily** from stored webhook facts + clock at read time (state machine in `packages/credits`); Stripe dunning drives the eventual `customer.subscription.deleted` webhook; auto-top-up is **request-time** (tech-spec §5: "triggered when balance < cost") — the trigger function (`maybeAutoTopup`) ships and is tested at M1, and its debit-refusal call site is wired by the M3 generation pipeline (Deferral Ledger row); expiry is derivation-time (never a cron) | R-18 unsettled the runner (Inngest's rationale was Vercel-bound); nothing in M1 *requires* a cron for correctness. Revisit: **M4 entry** (trend refresh genuinely needs a scheduler). | R-20 |
| D-M1-5 | Email dual-truth resolution (M1-entry obligation) | **Drop `users.email`** — Better Auth `user.email` is the sole email truth; every M1 billing need reads it **from the session** (checkout creation), and domain code continues to never query auth tables (M0 rule; the FK is a constraint, not a licence to join). This *structurally retires* the empty-email-guard obligation (no domain email column exists to guard); `bootstrapInTx` loses its `email` param | Leanest resolution the auth-swap deferral itself sanctioned ("sync-on-session or drop the domain copy"); kills the dual-truth class, not the symptom. Revisit: only if a domain-side email cache is ever needed for performance. | R-20 |
| D-M1-6 | Stripe→workspace resolution | The stored `stripe_customer_id → workspace` mapping (created at checkout-session creation, before redirect) is the **sole resolution authority**; Checkout metadata `workspace_id` is a cross-check only. Unknown customer, null/absent customer field, or metadata that **disagrees** with the mapping ⇒ recorded refusal (`refused_unknown_customer` / `refused_identity_mismatch`), 200 so Stripe stops retrying, zero ledger writes. Log lines for refused and ignored events carry **ids, never payload fields**: the event id, the outcome, and — where it makes the refusal diagnosable — the Stripe OBJECT id it concerns (invoice / session / PaymentIntent / subscription / customer id). Never an email, name, address or amount, and never the payload object itself (**wording corrected in round 7**: the original "event id + outcome only" was already exceeded by the `ignored`-path warn lines that name object ids, which the tenancy gate reads as compliant and which are what make a production refusal traceable; the invariant that matters is ids-not-PII) | Fail-closed on the non-session identity path; one authority, no fallback ladder (tenancy round-1 findings 3 and 8). Revisit: never on principle. | R-20 |
| D-M1-7 | Expiry vs partially-consumed lots | Balance is a **chronological lot-allocation fold** over ALL six kinds: `grant`/`pack`/`refund` and positive `adjust` are consumable **lots** (each with its own explicit `expires_at`, nullable only for `adjust`); `debit` and negative `adjust` **allocate** against live lots by the D-M1-8 order; `expiry` rows are materialization history — the fold **replays** existing expiry rows as events rather than recomputing them, so later rows (e.g. a refund after materialization) stay consistent. When a lot crosses its effective expiry with remainder > 0, the balance authority **lazily appends** an `expiry` row for the remainder — idempotent on the lot id, keyed to the **DB clock**, never a caller-supplied `at` (a historical `at` gives a pure read; writes only follow `now()`). Lock composition (billing round-2): when `deriveBalance` receives a **caller transaction** (the debit path, which already holds the per-workspace advisory xact lock), materialization **joins that transaction** — a same-session advisory re-acquire is a no-op, so no self-deadlock; the "own transaction under the advisory lock, on-conflict-do-nothing then re-read" design applies only to the bare-`db` read path (usage page). The Docker race suite carries the mixed case (a debit tx and a concurrent bare-db derivation over the same expired lot). A refund's `expires_at` is computed at refund time as the latest effective expiry of the lots its original debit consumed (a refund of expiring credits must not mint never-expiring ones) — **stated consequence, intended policy:** a refund of a debit whose lots have since expired is born expired and grants zero usable credits (fail-safe); goodwill credit is the admin `adjust` op with an explicit expiry, not `refund`. Invariant kept by test: after materialization, `sum(delta)` of ALL rows equals the fold's answer | The naive "sum of unexpired rows" (tech-spec §2 wording) over-subtracts once an expired grant was partially consumed — debits never expire. Lazy materialization keeps "the ledger is the balance" *literally* true, stays append-only, and needs no cron (D-M1-4). Kind-domain, concurrency, and clock rules pinned per billing round-1 findings 2–4. Revisit: if fold cost bites, snapshot rows — never a mutable counter. | R-20 |
| D-M1-8 | Lot consumption order | **Soonest effective expiry first**; equal expiry → older `created_at` first; still equal → grants before packs. Never-expiring lots (admin `adjust`) go last | Resolves the PRD-vs-tech-spec tension billing round-1 finding 5 named: REQ-G03 says packs are "consumed after monthly credits", tech-spec §5 says "oldest unexpired first" — a January pack is *older* than February's grant, so plain oldest-first burns the 12-month pack while the 1-month grant expires unused, contradicting REQ-G03's plain reading and the customer's interest. Soonest-expiry-first satisfies both documents in every case (grants expire in ≤1 month, packs in 12). Phase 4 task 9 syncs tech-spec §5's wording, citing this row. Revisit: never on principle. | R-20 |

## Risk Assessment (seeded from the brief's pre-mortem)

1. **Ledger correctness under concurrency/replay** (brief #1) — mitigations: single balance authority in `packages/credits` (Phase 2), Docker-Postgres race tests for double-debit and double-webhook (Phases 1–3), `stripe_events` + unique `stripe_event_id` double idempotency (D-M1-1), locking strategy proven by test not assertion.
2. **Engineering/evidence conflation on Stripe** (brief #2) — mitigations: keyless-provable handler tests via constructed events with signature verification isolated at the route edge (Phase 3), lazy Stripe client keeps the keyless build green, Phase 4 engineering-vs-evidence table + owner runbook; golden rule 9 task-level instruction to verify SDK shapes from installed types.
3. **Expiry/pause semantics drift** (brief #3) — mitigations: one module owns time semantics (Phase 2 `balance.ts`/`pause.ts`), table-driven cases enumerated from REQ-G02/G03/G08 + skill B4 (each rule row → ≥1 case), reviewer checklist B4 gates it.
4. **Webhook as tenancy hole** (codebase review) — the one non-session entry; mitigations: D-M1-6 fail-closed resolution, tenancy reviewer explicitly briefed on it, unknown-customer events recorded and refused.
5. **Migration 0001 vs adapter-owned tables** — FK into Better Auth's `user` survives only if its schema stays put; mitigation: FK named + tested on fresh PGlite migrate (Phase 1), and the auth CLI config is generation-only (never runtime).
