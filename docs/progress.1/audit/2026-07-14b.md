## Ranked register — new and elevated findings this run

### `[CRITICAL]` A. security — path traversal: unsanitized `vertical`/`platform`/`version` reach raw filesystem path construction with no containment check anywhere in the chain
- **Evidence, traced end-to-end by the audit chair:** `KnowledgeApiEndpoints.GetMechanisms(string vertical, string platform, ...)` ([KnowledgeApi.cs:24](src/KnowledgeApi/UgcIntelligence.KnowledgeApi/Api/KnowledgeApi.cs#L24)) and `GetLibrary(string version)` (`:115`) take raw HTTP-facing strings with **zero validation** anywhere in `Api/`, `Serving/`, or `Resolution/`. `MechanismResolver.KeyFor(vertical, platform) => $"{vertical}.{platform}"` ([MechanismResolver.cs:52](src/KnowledgeApi/UgcIntelligence.KnowledgeApi/Resolution/MechanismResolver.cs#L52)) is a bare string concatenation, and `ResolveByKey(key)` (or `version` directly, for `GetLibrary`) passes it straight to `reader.ResolveActiveVersion(key)`, which resolves to `ArtefactStore.PointerFor(prefix, key) => Path.Combine(_root, prefix, "pointer", key + ".json")` ([ArtefactStore.cs:96-97](src/ControlPlane/UgcIntelligence.Artefacts/ArtefactStore.cs#L96-L97)). `Path.Combine` does not collapse or reject `..` segments, and nothing anywhere in this chain checks that the resolved path stays inside `_root` (confirmed by reading `ArtefactStore.cs` and `PrefixScopedReader.Guard` in full — `Guard` only checks the *prefix* literal, e.g. `"mechanisms"` vs `"patterns"`, never the resolved path). `File.Exists`/`File.ReadAllText` then resolve `..` at the OS level, so a crafted `vertical`/`platform`/`version` value can escape `_root` entirely. `File.ReadAllText` is called **before** the sha256 verification (`ArtefactStore.cs:62-73`), and if the traversed read succeeds but the resulting "key"/pointer content is malformed (e.g. under 2 characters, hit by `sha[..2]` in `PathFor`), the resulting unhandled exception is not one of the three types `KnowledgeApiEndpoints` catches — producing exactly the bare `500` the design's own doc comment (`KnowledgeApi.cs:9`, `component-4-knowledge-api.md:154`) promises never to return. No test anywhere in `tests/Architecture` exercises this (grep for `Traversal`/`PathFor`/`KeyFor` under `tests/` returns nothing).
- **Attack:** `GET /api/knowledge/mechanisms?vertical=..%2f..%2f..%2fsome&platform=path` (or a `version` value doing the same for `/libraries/{version}`) attempts to read `*.json` files outside the artefact-store root. Note (correction to the security critic's original framing): the `id` path parameter on `GetMechanism`/`GetExemplars` is **not** part of this vector — it's only compared in-memory against already-loaded mechanism IDs (`m.Id == id`), never used in a filesystem path. The vulnerable parameters are specifically `vertical`, `platform` (feeding every cohort-scoped endpoint), and `version` (feeding `GetLibrary` directly).
- **Fix:** Validate `vertical`/`platform`/`version` against a strict allow-pattern (e.g. `^[a-z0-9_-]+$`) at the `KnowledgeApiEndpoints` boundary before they reach `KeyFor`/`ResolveByKey`; add a defense-in-depth check in `ArtefactStore.PathFor`/`PointerFor` that the resolved, fully-qualified path is still rooted under `_root` (e.g. `Path.GetFullPath(path).StartsWith(Path.GetFullPath(_root))`).
- **Owner:** control-plane-engineer
- **ADR:** none exists; add a security addendum to ADR-0007 stating the read-grant is bounded by *validated* keys, not just a prefix string.

### `[CRITICAL]` B. veto-verdict-integrity / money-exploration — the already-known DisclosureDetector fail-open bug is reused verbatim in Gate B's live-post re-check, so it can wave an undisclosed paid post through the hard gate that stands between it and client amplification spend, and writes a false "verified" fact into the permanent event log
- **Evidence, confirmed by the audit chair:** `LiveDisclosureChecker.Check` ([LiveDisclosureChecker.cs:42](src/ControlPlane/UgcIntelligence.C2.Api/GateB/LiveDisclosureChecker.cs#L42)) calls `DisclosureDetector.Evaluate(publishedFeatures, publishedPost, ...)` — **the identical detector** already found in run 1 (finding #4) to fail-open (`Pass`) when `features` is null and the caption alone shows no claim/sponsorship marker, before ever reaching the degraded-mode branch. `LiveDisclosureChecker.cs:46` computes `verified = !veto.Fired && veto.Evaluable` — and `VetoResult.Pass(...)` sets `Evaluable: true` — so the same carve-out that made V1 pass at Gate A now makes `Verified = true` for a **published** post whose disclosure was never actually inspected. `HardGates.cs:74-76` gates money release solely on `facts.LiveDisclosure.Verified`; `SignoffService.cs:33` re-runs the same `HardGates.Evaluate` at sign-off, but it's the same detector both times, so the "runs twice" backstop does not catch it. The resulting boolean is then persisted as ground truth in `PostPublished.live_disclosure_verified` (`GateBEventEmitter.cs:15-28`), an event field `events-v1.json:121-122` documents as existing specifically because "the compliant artefact and the published artefact are different objects" — this is precisely the record that field exists to protect, and it can be silently wrong. No test constructs `LiveDisclosureChecker.Check(null, post)` with an unsponsored/no-claim caption.
- **Drift path:** organic UGC later selected for paid amplification (Gate B's entire purpose) is exactly the profile likely to have `IsSponsored=false` at original submission and a caption that never names the product (a visual/spoken claim, not textual) — precisely the combination that trips the carve-out. Extraction lag/failure on the live artefact at T+24h is the ordinary case, not the exotic one.
- **Fix:** Same fix as run 1's finding #4, applied once at the detector level so both call sites inherit it: when `features is null`, an inconclusive caption reading must return `Unevaluable`, never `Pass`. Add a dedicated `LiveDisclosureChecker` test for null-features + unsponsored + no-caption-claim.
- **Owner:** control-plane-engineer
- **Note:** this supersedes run 1's finding #4 — same root cause, now confirmed to have double the blast radius (compliance veto **and** money-gate) plus a permanent-record integrity consequence. Track as one finding, not two.

### `[HIGH]` C. component-boundaries — the Knowledge API's `GetLibrary` endpoint is the one C4 surface that doesn't gate on ratification/lexicon, and the doc conflict this raised across two critics resolves against the code
- **Evidence:** `KnowledgeApiEndpoints.GetLibrary` ([KnowledgeApi.cs:115-130](src/KnowledgeApi/UgcIntelligence.KnowledgeApi/Api/KnowledgeApi.cs#L115-L130)) composes **every** mechanism in the resolved manifest unconditionally (`lib.Mechanisms.Select(m => ResponseComposer.Compose(m, lib))`) — unlike `GetMechanisms`/`GetMechanism`/`GetExemplars`, which all gate through `WarrantFilter.IsServed` first. `MechanismResolver.ResolveByKey` itself does no filtering — it returns the whole parsed `MechanismLibrary` regardless of ratification state, by design (filtering is meant to happen at the endpoint layer, which `GetLibrary` skips). It also hardcodes `Coverage.Served.ToSnake()` regardless of actual served count, so a wholly-falsified historical version would report `coverage.state: "served"` with `served: 0`.
  - **Chair's adjudication of the doc conflict:** two critics read `component-4-knowledge-api.md` and disagreed — architecture called this a violation of "What C4 never does" (line 168: *"It never serves an unratified statement. It never serves a `falsified` or `conjectured` mechanism as active"* — stated with no carve-out) and ADR-0006 (*"a mechanism without them is never served"*); the invariant-drift critic called it intentional, citing line 129 (*"the immutable manifest, for reconstructing a response served months ago"*). Reading both sources directly: line 51 of the same doc states *falsified/conjectured mechanisms "ship inside the artefact for auditability and are **never returned as active**"* — the artefact (storage) and what's returned (serving) are explicitly distinct concepts. And the endpoint's own stated purpose — *reconstructing a response **served***, not dumping the artefact — is incoherent with "unconditionally return everything in the file," since a falsified/conjectured mechanism was by definition never served as active at any point in time. **The text supports architecture's reading, not invariant-drift's.** No line in either doc actually carves out `/libraries/{version}` from the "never serves unratified/falsified-as-active" rule.
- **Mitigating factor, stated honestly (both critics agreed on this part):** the real Python producer (`publish_library`) already refuses to publish an unratified served-rung mechanism and excludes `conjectured` from what it writes — so *if* that's the only writer that ever exists, this can't currently be forced to leak anything. But no writer is wired to any real filesystem/blob layout yet (run 1 finding #3, reconfirmed this run) and no host serves this endpoint at all — so C4's own code enforces none of this independently, for an invariant its charter says is C4's alone to hold.
- **Fix:** Route `GetLibrary` through `WarrantFilter.IsServed` per-mechanism (marking non-served entries explicitly in the historical view, since reconstruction is the point), and reuse `ResponseComposer.ComposeCoverage` instead of the hand-rolled `Coverage`. Add a test asserting an unratified/lexicon-dirty mechanism is never returned with its raw statement from `/libraries/{version}`.
- **Owner:** control-plane-engineer
- **ADR:** revise ADR-0006 §6 to state explicitly whether `/libraries/{version}` is a carve-out and what it may show for a non-served mechanism — the ambiguity that produced two conflicting critic readings is itself worth closing.

### `[HIGH]` D. correctness — the Knowledge API can throw an unhandled exception (a bare 500) on a hash-valid-but-malformed artefact, contradicting its own "never a bare 500" invariant
- **Evidence:** `MechanismLibrary.Parse` (`Mechanism.cs:106-111`) throws `JsonException` on malformed JSON; called uncaught inside `MechanismResolver.ResolveByKey`'s only try/catch (`MechanismResolver.cs:98`, which catches `ArtefactHashMismatchException`/`ArtefactNotFoundException`/`MechanismStoreUnreachableException` but not `JsonException`). Same pattern for `ExemplarIndex.Parse` (`ExemplarIndex.cs:32-35`), called uncaught at `KnowledgeApi.cs:79`. `Views.cs:101` documents "a bare 500 is never produced."
- **Fix:** Catch `JsonException` in `MechanismResolver.ResolveByKey` and `KnowledgeApiEndpoints.GetExemplars`, mapping to `ResolveStatus.StoreUnreachable`/`Unavailable`, same as the existing hash-mismatch handling.
- **Owner:** control-plane-engineer

### `[HIGH]` E. security — the `Untrusted<T>` prompt fence has no anchor at the domain layer (elevates run 1's LOW #21 — same root cause, sharper framing)
- **Evidence:** `Submission.Caption` and `FeatureRecord.Transcript`/`OnScreenTextSpan.Text` are plain `string` ([Submission.cs:17](src/ControlPlane/UgcIntelligence.Domain/Entities/Submission.cs#L17), [FeatureRecord.cs:55-56](src/ControlPlane/UgcIntelligence.Domain/Entities/FeatureRecord.cs#L55-L56)). `FencedPrompt.Build` only accepts `Untrusted<string>`, but has **zero production callers anywhere in `src/`** — only test fixtures construct one. There is therefore no code path today that takes a domain string and marks it untrusted before it could reach a prompt; the type barrier only exists once a value has already been manually wrapped, and nothing forces that to happen.
- **Fix:** Change `Submission.Caption`/`FeatureRecord.Transcript`/`OnScreenTextSpan.Text` to `Untrusted<string>` at construction (the extraction/ingestion boundary), so the compiler — not a convention — forces every future consumer through `ExposeForProcessing()`/`Fencing.Fence()`.
- **Owner:** control-plane-engineer (when the real scoring endpoint is wired)
- **ADR:** revise ADR-0002 to require `Untrusted<T>` at the domain-entity level, not only at `FencedPrompt.Build`'s signature.

### `[HIGH]` F. tenancy / measurement-discipline — the Python internal-corpus assembler has no structural tenant-scoping barrier, unlike every other tenant boundary in the codebase
- **Evidence:** `internal.py`'s `replay()` ([internal.py:140-254](src/IntelligencePlane/c1_pattern_engine/corpora/internal.py#L140-L254)) accepts events spanning any number of tenants with no tenant filter anywhere in the fold — contrast `TenantScopedRepository<T>` (no unscoped method exists) and `PatternRepository` (keyed on `(tenant_id, vertical, platform)`, no widening parameter). No function converts `AssembledRecord` → `InternalPost` yet (confirmed by grep), and no test feeds `replay()` two tenants.
- **Fix:** Give `replay()` (or its caller) a tenant-scoping guard symmetric to `PatternRepository`'s; add a test asserting two tenants' events cannot fold into one estimate.
- **Owner:** intelligence-plane-engineer
- **Note:** currently vacuously compliant — no caller exists yet — but is "one integration PR away from silent drift" per the invariant-drift critic, echoing the same "compliant only because unwired" shape as findings A/C/E.

## Hunches (not promoted)

- `[HUNCH]` (security) `MechanismArtefactReader`'s `IOException`-only catch may misclassify a genuine `UnauthorizedAccessException` (AV lock, not a deliberate prefix violation) as an uncaught bare 500 rather than a 503 — not fault-injection-tested.
- `[HUNCH]` (security) A malformed/hallucinated model-raised veto ID string (e.g. free text instead of `"V1"`) is never validated against the known V1-V6 set before surfacing — display-hygiene concern, surfaced-only, never reaches a decision.
- `[HUNCH]` (data) `AssembledRecord` in `internal.py` keys purely on `submission_id` with no cross-check that a later event's `tenant_id` matches the record's original tenant — UUID collision across tenants isn't realistic, but a mislabeled/malformed event wouldn't be caught either.
- `[HUNCH]` (data) `n_cohorts`/`cross_cohort_recurrence` in the mechanism synthesiser is described as "counted by cross-referencing other mechanism libraries," but the code that performs this cross-referencing wasn't located — if it ever pools raw exemplar data across cohorts rather than counting library metadata, that would be exactly the cross-population aggregation ADR-0006 forbids.
- `[HUNCH]` (correctness) `ResponseComposer.CorpusDate` treats an unparsable `CutAt` as `null`, which makes `stale` compute to `false` — a malformed corpus date silently avoids the staleness flag instead of erring toward staleness.
- `[HUNCH]` (accessibility) `VerdictPanel`/`AmplificationPanel` submit buttons have no in-flight/pending state — a fast double-click before the promise resolves could fire the action twice; only single-click is asserted in tests.
- `[HUNCH]` (operability) `.claude/hooks/post-edit-check.js` runs a full `dotnet build` + architecture-test suite on every `.cs` edit with a 300s timeout — on a real host this could be slow enough that a future contractor disables the hook out of impatience, silently losing the enforcement layer finding I depends on.
