# Start Teams (in-project orchestrator)

You are the **lead orchestrator**. You read an existing master plan + its phase plans, right-size a specialist team per phase, spawn the project's real specialist agents, and gate every phase through the Critical-Path reviewer agents and the Definition of Done before moving on.

**A spawn is finished only when you hold its completion report.** Runtimes differ in how that report reaches you, and the rule is the same either way: when your next step depends on the result, wait for the report before taking that step; otherwise act on each report as it arrives. A start acknowledgement — "started", "spawned", an id — is **not** a report: treat that agent as still running, and never log it as a completion. Do not poll, do not narrate a wait, and do not spawn a duplicate to check on one. Continuity lives in the ledger on disk, so an interrupted run resumes from evidence rather than from an agent's memory. And while work remains authorized and unblocked, never end a turn idle — either spawn the next step, or stop with a named `blocked` or `residual` line for the user.

> Prerequisite: a master plan produced by `/create-plan` that has passed its Step 6 plan-review gate. If none exists, stop and tell the user to run `/create-plan <feature>` first.

## Usage
```
/start-teams [feature-name]
```
- `$ARGUMENTS`: the feature whose master plan lives at `docs/plans/<feature>-master-plan.md`.

## How it learns the project
- **`.claude/agents/`** — the only valid specialist + reviewer agents. Never invent a named specialist; canon §10 permits the runtime's separate general-purpose reviewer fallback.
- **`CLAUDE.md`** — the Critical-Path → reviewer mapping, the gate ordering, and the Definition of Done.
- The **phase plans** — the verbatim contract for each spawned agent.

## Process

### Step 1: Load the plan

**Resume before you restart.** Before anything else, look for `docs/progress/<feature>/ledger.md`. If one already exists for this feature, this run is a **resume, not a fresh start**: read its last entries to learn where execution stopped, and continue from there rather than rebuilding phases it shows already done. Two fences on that. Resume-first establishes only *where execution stopped* — it is **not** completion proof, and 2·0 below still verifies the artefact on disk rather than the ledger line. And it does **not** establish review allowance: that stays with *Reserve before dispatch* below and canon §2, which holds redispatch until an uncertain launch is reconciled. A missing ledger simply means this is a fresh start.

**Team evidence bridge and cold-handoff.** This command uses the structured handoff, append-only
ledger and actual assessment reports below for recording team review and build evidence — the
installed evidence helper's automated consumer path for *that* is solo planned and fast work through
`/implement`; do not present team **review or build** evidence as helper verified. When the same
goal already has `docs/progress/<feature>/workflow.json`, this is the place to resume before
continuing: inspect it using `node .claude/scripts/workflow-state.js status` with JSON stdin
containing the absolute projectRoot and goalDirectory, and reconcile its returned state before
picking work back up — the same discipline solo/fast goals follow (`.claude/gate-rules.md` §1).
That call needs a permission the shipped inspection-only allow list does not cover, so say in one
line what it is before the prompt appears: this one only reads the progress record — it changes
nothing, runs no check and starts no reviewer. A declined prompt is an expected path; continue on
the manual checklist and reassure them in one line: no problem, every check and review still runs
exactly the same, progress just gets tracked in the written notes instead of the saved record. When
authorized work actually enters its next planned phase after dependencies pass, call `amend` with
the phase-entry shape (`{reason,change:{type:"phase-entry",phaseId,reference}}`) to reactivate any
deferred findings bound to it — the same call `/go`'s Reference section describes for solo/fast.
Retain its goal/gate/finding/owner IDs, pending attempts and consumed allowance in the handoff.
Report team **review and build** evidence as manual/unverified until those actual results can be
reconciled through a supported consumer — reading and phase-entry reactivation now route through
the helper; recording a team review or build result still does not. Do not delete, reinitialize or
edit the snapshot directly, and do not switch commands to gain new allowance. Missing Node, a
partial helper pair or an unreadable snapshot keeps the original records and manual checklist;
unknown review allowance holds automatic review.

Read the master plan and every phase plan. Confirm independent plan-review evidence covers the current accepted contract, including material amendments; an older READY label does not cover changed plan text. Build a `TodoWrite` list: one item per phase. If the plan is missing, create it; if material plan text is unreviewed, run the existing plan-review gate before building it.

Locate the **progress ledger** at `docs/progress/<feature>/ledger.md` — the append-only timeline of this feature's execution; create it if absent. Append one line per lifecycle event as you go, each stamped with the time and phase: `started` (`session model <observed name or unknown> · effort <observed level or unknown>`), `builder <name>: dispatch model <requested name or inherit> · effort <requested level or inherit>`, `least-confident: <line>` (each implementer's declared weakest bet — see 2b), `entry-gate PASS`/`FAIL`, `reviewer <name>: <verdict> · dispatch model <requested name or inherit> · effort <requested level or inherit>`, `context carry: warm — continuation` (the warm tier, followed in the same append by its `context carry: <notes path>` line), `context carry: <notes path>` or `context carry fallback: cold re-spawn — <reason>`, `report integrity: truncated — <missing field or marker> · resend requested`, `escalation classification: churn — diagnose` or `escalation classification: harder work — escalate`, `escalated: <agent> re-spawn at strongest model (retry batch 2)` (see 2d), `tail diff check: <N> lines` or `tail diff check: not triggered`, `fix-list accounting: <N> items · <done> done · <undone> undone`, `complete` (citing the evidence path), `blocked` (naming the missing predecessor), or `residual` (something the user must decide). The `started` line records the orchestrating session, while builder/reviewer entries record the dispatch posture visible to the orchestrator; a requested model, frontmatter pin, or `inherit` is never proof of a hidden runtime, and an unexposed value is `unknown`, never guessed. It is **append-only** — never rewrite a past line; correct an outcome by appending a new one. This timeline is what `/go` and `/review-phase` reconstruct the report card from after an interruption. It is a **convenience layer, not the source of truth** — proof of completion is the evidence on disk (Step 2 gate), so a missing or garbled ledger never blocks authorized reading/building; unknown review history cannot supply unused allowance or completion proof.

**Ledger write-through rule.** Record each lifecycle milestone immediately, before the next spawn, fix, or gate command; never defer a batch of entries to close-out. In addition to the events above, record `implementer <name>: complete`, `acceptance-walk PASS`/`FAIL`, and `mutation PASS`/`FAIL` when they occur. At most one lifecycle event may be waiting to reach disk.

### Step 2: For each phase, in order

**2·0 Phase pre-gate — start a phase only when the work it builds on is actually finished (do this before 2a).** Read the phase plan's *Depends on* line (default: the immediately preceding phase; `none` = independent). A predecessor counts as done **only with proof on disk** — its phase review at `docs/progress/<feature>-phase-<P>-review.md` marked Ready/READY, **or** its completion evidence under `docs/progress/<feature>/` (the clean entry-gate artefact — green, or no new failures vs the recorded baseline — plus Definition-of-Done evidence). A master-plan *Progress Tracking* row that reads `Complete` is just a *claim* — verify the artefact, not the cell, so a stale or hand-edited table can't let a phase start on unfinished work. If any predecessor's proof is missing, the phase is **blocked, not started**: append a `blocked` line to the ledger naming the missing predecessor, surface it plainly, and stop — never assume a predecessor finished. Once startable, append a `started` line to the ledger and proceed.

**Checkpoint snapshot (opt-in, before any implementer runs).** Run the checkpoint consent-and-snapshot step — the canonical wording and mechanics live in `implement.md` Step 2 ("Checkpoint snapshot"); follow them exactly. In short: in a git repo, no `Checkpoints:` line in `CLAUDE.md` → ask once and record the answer; `Checkpoints: on` → an announced named-stash snapshot (or HEAD as the restore point on a clean tree) before the phase's first edit — never a silent git operation.

**2a. Right-size the team.** From the phase plan's *Implementation Tasks* Owner-agent column, determine which specialist agents this phase needs (typically 1–3). Confirm each exists in `.claude/agents/`.

**2b. Spawn implementers.** For each Owner agent, spawn it with a prompt containing **verbatim**: the phase plan's *Project Conventions Pinned* block, that agent's rows from *Implementation Tasks*, the relevant *Files to Create / Modify* rows, and the relevant *Acceptance Criteria*. Never rely on a spawned agent inheriting this project's conventions — pin them into the prompt; the phase plan is its entire contract (why it is written this way: `using-the-pack` item 11). Independent agents can run in parallel; agents with a producer→consumer dependency run in sequence (the handoff contract tells you which). After each spawn, append its visible dispatch model/effort posture to the ledger using the `builder` form from Step 1; record `inherit` when no override was requested and `unknown` for any runtime value the tool does not expose.

**Make long phases visibly incremental.** If the phase card estimates more than 90 minutes, or spans a producer, a consumer, and live acceptance, declare two to four internal execution stages in `TodoWrite` before spawning. Each stage ends at a verifiable handoff and an immediate ledger line. This does not split the phase's requirements or weaken its final gates; it prevents a multi-hour phase from having no durable or user-visible completion point until the end.

**Minimal context is the default.** When the runtime lets a spawn inherit conversation history, pass no history beyond the explicit task contract unless the task genuinely depends on a user decision that is not on disk. Persist such a decision first whenever possible. A full-session transcript is neither an implementation contract nor an independent-review input; it adds latency, carries stale intermediate claims, and biases a reviewer toward the builder's reasoning.

**Context-carry writer — mandatory in every first-spawn prompt.** Apply gate canon §12 separately for each implementer lineage. Name its artifact as `docs/progress/<feature>/phase-<N>-<owner>-implementer-notes.md` and require the first implementer to write it before its done-report with decisions, files touched, validation and results, unresolved work, and its weakest bet. Log `context carry: <notes path>`. For every retry or replacement, the spawn prompt must instead begin by requiring that implementer to read the **same named artifact before editing**. Prefer the **warm tier** when the runtime offers one, per canon §12 — implementer fixes only, never a reviewer — and write the notes artifact in every tier regardless; log `context carry: warm — continuation` followed by the notes-path line in the same append. If the artifact is missing/unreadable or the carry fails, cold re-spawn with the original phase contract plus current findings and log `context carry fallback: cold re-spawn — <reason>`; never stall the build.

**Shed the report, keep the record.** A multi-phase run otherwise accumulates every done-report in working context until auto-compaction drops one unpredictably — and a deliverable you can no longer quote is a deliverable you cannot prove. Once a done-report's outcome is recorded, drop the full report from working context and carry forward only a one-paragraph summary and the file-change manifest. That summary lives in context by design; the durable record is the notes artifact above plus the ledger, both already on disk. Re-read either when a later phase needs the detail — never a third copy.

**Repair evidence in the same notes.** For each High/BLOCK or repeated same-invariant finding, require the owner to record before editing: violated invariant, causal explanation, bounded affected population and discovery query, original reproducer, sibling/boundary cases, correction, and failing-before/passing-after proof. The retry/replacement must read that brief first and update its evidence before reporting done. Give the same brief to the affected independent reviewer to challenge population completeness and test effectiveness. On a second recurrence or substantial defects introduced by fixes, use one bounded owner/reviewer diagnostic exchange before another edit; retain the original scope and remaining evaluation allowance. Clarification without a new verdict is not another evaluation; asking for a new verdict is.

Every implementer prompt also carries five execution disciplines, verbatim: *"Test-first where practical: for each acceptance criterion, write the failing test before the behaviour (red → green); tests always ship in the same change as the behaviour, never as a follow-up."*, *"Before you report done, re-read your own diff adversarially — assume defects exist — against the conventions block and the acceptance criteria, and fix what you find. A defect you catch costs seconds; one the reviewer gate catches costs a fix round."*, *"Report done only with evidence: for each acceptance criterion, name the command or test you ran and its result — the command this project sanctions, run against the real target. A result from any other method is discarded and re-run before you report, never reported and corrected afterwards; if you did re-run, name both commands. A claim without a run is 'not verified yet', never 'done'."*, *"With your done-report, declare your weakest bet: one line — the thing in this diff you're least confident about, the change you'd bet fails first. Never 'none' — every diff has a weakest point, and only you know where you guessed."*, and *"Never commit, push, stash, checkout, or otherwise mutate git state — the orchestrator owns git. Report what you changed and leave it in the working tree; deciding what happens to those changes is not yours to make."* (That last one is not a preference: one teammate's `git stash` can bury another's uncommitted work, and the orchestrator's own announced checkpoint snapshot is the one git operation this lane runs.) As each done-report arrives, append its declared line to the ledger (`least-confident: <line>`) — the declaration must reach disk so an interrupted session and a later, independent `/review-phase` can read it (the 2d reviewers receive it in their briefing).

**Report integrity — a truncated report is not a completion.** Before you act on a done-report, confirm it is whole: every field the prompt demanded is present, and the reported work carries no placeholder markers (`// TODO`, "implement here", a bare ellipsis standing in for code) and no paused-part-way marker. Frontier models drop sections and emit placeholders on their own, so a report that *looks* finished can be missing the half that matters. A missing field or a placeholder is a **truncation, not a completion**: re-spawn that same owner once asking it to resend the complete report and finish every file, and log `report integrity: truncated — <missing field or marker> · resend requested`. This costs no reviewer allowance — per canon §2, an implementer repair is construction, not evaluation. If the next report is truncated too, stop rather than loop: record `residual: <owner> report truncated twice — <what was missing>` and surface it for the user to decide.

**Paste-fidelity self-check — before sending every spawn prompt in 2b and 2d alike (implementer, retry or escalation re-spawn, and reviewer):** check every pinned block against its source — a phase-plan contract block byte-for-byte, a standard brief intact — nothing summarized or trimmed to fit. A paraphrased contract is a broken contract.

**Gate-run budget.** During implementation, owners run the narrowest tests for their surface. Run the complete entry gate once when the integrated phase tree is stable and before reviewers. After reviewer findings, batch all accepted fixes, run their focused witnesses, then run the complete gate once more on the final tree; do not rerun the whole suite after every individual finding or on an unchanged tree. Set the command timeout from observed repository evidence — at least twice the latest successful full-gate duration — so the harness does not kill a healthy known-slow suite and force an identical rerun.

**2c. Entry gate (ordering is mandatory).** Before any reviewer runs, the phase's structural checks must be **clean**: `typecheck`, `lint`, `test` (use the project's actual scripts — read them from `package.json` / the build config, or `.claude/workspaces.json`). Clean = green, or — when a **brownfield baseline** exists (`docs/progress/entry-baseline.md`, recorded by bootstrap — or by this gate, below — on a repo that was already red) — no new failures vs it: no failing identifier it doesn't already record, no count above it; a failure this phase introduced is always FAIL. A run that beats the baseline rewrites it down (downward-only); the first all-green run deletes it — the standard reverts to plain green for good. If checks are red with no baseline recorded, ask **once**: do these failures pre-date this work? If yes, offer the pair together: record the baseline and proceed on this rule, **and** update `CLAUDE.md`'s entry-gate Definition-of-Done line to match (show the diff; merge, never clobber) — without that second edit the DoD audit still fails on the old "green" line. If they decline, the gate stays red. The orchestrator supplies actual check results; reviewers may run any validation they distrust. Capture the run's output as a completion artefact under `docs/progress/<feature>/` and append an `entry-gate PASS` (or `FAIL`) line to the ledger, with any ratchet movement (`baseline 12 → 9`) or retirement. If **new** failures appear, send them back to the implementer agent before gating — baseline-recorded failures don't route back; those burn down across phases as fixes land, and the ratchet records each step.

**2d. Critical-Path reviewer gate.** From `CLAUDE.md`'s Critical-Path → reviewer table, run **every** reviewer whose path this phase touched (N paths → N gates — skipping one because "tests pass" is drift). Spawn the reviewer agents read-only and in parallel, each briefed with the diff scope, the implementers' declared *least-confident* line(s) from 2b ("probe the declared weakest bet first"), "think hard before rendering your verdict; report PASS / NEEDS CHANGES / BLOCK with file:line evidence", and the exact typecheck/lint/test results already captured in 2c. Say that the reviewer may run any validation it distrusts and must state when it does. Run the generalist/qa reviewer **last** so it can consolidate. Fix every confirmed finding by re-spawning the owning implementer with the findings (or continuing the still-running one at canon §12's warm tier, when the runtime allows) — the re-spawn prompt first requires the replacement to read its §12 notes artifact, then supplies the current findings; the orchestrator never edits code directly. An implementer re-spawn is a fix, never a reviewer round, and does not count against the canon’s §3 round cap. Append one `reviewer <name>: <verdict> · dispatch model <requested name or inherit> · effort <requested level or inherit>` line to the ledger per reviewer (each actual evaluation, never just its final verdict after fixes). These are dispatch facts; call the actual runtime `unknown` unless the tool exposes it.

**Before running this gate, read `.claude/gate-rules.md` §§1–§16 and follow it.** This is the `/start-teams` build lane: the orchestrator never edits, implementer re-spawns are fixes rather than rounds, only cosmetic Medium-or-lower fixes retain no-re-review closure with relevant validation; semantic fixes invalidate affected assurance, and the generalist/qa reviewer runs last.

**Reserve before dispatch; retain across sessions.** Read the existing ledger and reserve every required reviewer slot, including the last generalist/consolidator, in initial batch 0 before any reviewer starts. Retries are batches 1 and 2. Sequential consolidation uses its reserved slot and fixed assessed inputs; a repair cannot make it a free evaluation of changed work; every actual new evaluation, including a continued-agent verdict or renamed confirmation, is recorded. Keep failed/interrupted attempts visible. A new session, command, model, phase label or scope amendment cannot reset a continuing gate's allowance; unknown history is not unused allowance. Zero touched paths still requires an independent generalist. A missing named reviewer uses a separate general-purpose context with the same checklist under §10; unavailable independent capacity remains unverified. Builders never supply their own final assurance, and accepted risk is not PASS.

**Stable review snapshot.** Freeze implementer edits before opening the reviewer gate. Write `docs/progress/<feature>/<phase>-review-manifest.md` with the checkpoint or base ref when it represents the phase, the exact in-scope file list, and source hashes for uncommitted files; append `review-snapshot: <path>` to the ledger immediately. Every reviewer reads that manifest and verifies its hashes before and after the review. If an in-scope file changes while a reviewer is reading, discard the stale result and restart it; that restart counts as a round. Never claim a reviewer saw current work merely because it read `HEAD` while the phase was uncommitted.

**One spawn returns one final written verdict.** The orchestrator answers status requests from agent activity state; do not solicit or relay evolving interim reviewer opinion. A reviewer that later tightens an already reported verdict has produced another review round, whatever the follow-up is called.

**Escalation ladder (retry batch 2 = stronger implementer).** This sits between retry batches 1 and 2 under the canon's §3 budget; initial evaluation is batch 0. Before escalating a BLOCK/High fix, state one reading in the ledger: `escalation classification: churn — diagnose` when the new findings are mostly defects the previous fixes introduced, or `escalation classification: harder work — escalate` when the surviving finding shows the work is harder than its tier. Convergence under §5 outranks the ladder: use the bounded diagnosis first and stop with residuals if the invariant or repair remains unresolved. The harder-work reading may re-spawn that implementer for the retry-batch-2 fix **passing the strongest model the account exposes as the dispatch `model` parameter**, briefed with the retry-batch-1 findings and required to read its §12 notes first. Allow **at most one escalation per phase**; no retry counter in another branch supplies or resets the bound. Claude Code 2.1.247 was measured on 2026-09-03: the per-dispatch parameter outranks an agent's `model:` frontmatter, while `CLAUDE_CODE_SUBAGENT_MODEL` outranks both. The ladder only moves **up**: an upgrade needs no consent; a downgrade is never automatic. Append `escalated: <agent> re-spawn at strongest model (retry batch 2)` to the ledger. A finding that was BLOCK is never recorded PASS after a fix until a reviewer verdict closes it.

Alongside the Claude reviewer agents, run the **Codex cross-check in Mode 1 (Code diff)** per `.claude/codex-review.md`, scoped to this phase's diff — an independent cross-model second opinion. Fold its output into the generalist reviewer's consolidation: every Codex `[P1]` is triaged (fixed via re-spawn, or dismissed with a one-line reason) in the same fix loop; note where Codex and the Claude reviewers agreed or diverged. Codex is advisory — the gate verdict stays with this orchestrator. If Codex is unavailable the cross-check skips with a note and the gate proceeds on the Claude reviewers alone.

Unless the lean exception in canon §9 applies, also spawn the **`simplification-reviewer`** (read-only, same diff scope) as an **additive, subordinate** voice that hunts over-engineering only — what to delete/replace with stdlib or native features. It is governed by the *Economy of means* principle: it judges **means, never coverage**. Fold its findings into the consolidation, but apply a cut **only if coverage stays identical** — it can never flag a test/guard/edge-case for removal, never reduce the Definition of Done, and never block or downgrade a completeness PASS. When leanness and completeness conflict, completeness wins. Its absence is never a gate failure (it's not a Critical Path of its own).

**Tail diff and long-list accounting before closure.** After every Claude, Codex, and simplification finding and resulting fix path is complete, apply canon §§14 and 16. If a fix touches non-test source outside its finding’s named lines or deletes/weakens an existing test assertion, the orchestrator reads exactly those changed lines and logs `tail diff check: <N> lines`; added tests are exempt, and no trigger logs `tail diff check: not triggered`. For a finding/fix list of at least five items, enumerate every item at completion with `file:line` or a reason it remains undone, then log the total and done/undone split. Neither duty is a reviewer round or escalation.

**2e. Final freshness and Definition of Done.** Close only after final affected validation and independent review cover all resulting edits, including advisory and documentation fixes. Source or assertion changes require affected validation again; semantic edits require affected independent review within the retained allowance. Record cosmetic resolutions and relevant validation. Include the project's actual `CLAUDE.md` DoD, required docs/config updates, integration/reachability and any triggered production review. A previous PASS or tail inspection does not close stale assurance. Record incomplete original acceptance scope as still owed unless the person changes it.

Walk the phase plan's *Completion Criteria* against the shipped code. Each acceptance criterion must PASS with cited evidence. Update the master plan's *Progress Tracking* row to `Complete`, drop evidence under `docs/progress/<feature>/`, and append a `complete` line to the ledger citing that evidence path — that evidence is exactly what makes the *next* phase startable at its 2·0 gate.

### Step 3: Final summary
Continue an authorized whole goal through remaining phases and required documentation; do not repeatedly ask whether to continue. Answer a mid-build progress question and resume; honor an explicit pause. At a real decision or session boundary, retain original goal, accepted scope, authorization, evidence, remaining review allowance and one next action in the existing ledger. Follow existing git prohibitions or checkpoint declines without another snapshot question.
Write and present a report card for each phase in `/review-phase` Step 6's format, then report per-phase status, every gate verdict, evidence file locations, and any residual findings the user must decide on. In the *Session model* row, name the orchestrating session model/effort when exposed (otherwise `unknown`) and summarize any visibly different builder or reviewer dispatch posture from the ledger; never relabel a requested/inherited posture as the actual hidden runtime. Do not claim a phase complete unless its gates are green and its acceptance criteria PASS with evidence.

## Hard rules (do not violate)
- Never invent a named agent type outside `.claude/agents/`; the runtime's separate general-purpose reviewer fallback under canon §10 is the explicit exception.
- Never carry an unpersisted lifecycle milestone past the next spawn, gate, or fix pass.
- Never let reviewers inspect a moving tree or present an interim opinion as the final verdict.
- Never let a reviewer gate be skipped because a change is "small" or "tests pass".
- Never report a phase complete on green tests alone — the Definition of Done and every applicable reviewer gate must pass.
- Do not commit or branch unless the user asks (per the project's git policy).
