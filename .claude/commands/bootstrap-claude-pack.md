# Bootstrap (the generator)

The pack ships **generic machinery** (the guardrail engine, the post-edit-check engine, the orchestration commands, generic reviewer agents). This command turns that machinery into a setup **tailored to this specific project**: it derives the non-negotiable rules, writes enforceable guardrail rules, generates project-specific reviewer agents, and authors Critical-Path skills.

> Run this **once per project**, right after installing the pack. Re-run it later when the architecture changes materially (new module type, new external integration, new compliance constraint).

## What "tailored" means

For your repo, "tailored" ends up as: a `CLAUDE.md` of non-negotiable rules with a **Critical-Path → reviewer mapping** table, write-time guardrail rules enforcing those paths, a reviewer agent per Critical Path, and matching Critical-Path skills. Your job is to **discover this project's Critical Paths from the codebase and the user**, then generate those artefacts. (The reference project this pack was extracted from comes up again in Phase 2 and the Rules — never copy its domain rules; derive this project's.)

## Process

Use `TodoWrite` to track these phases.

### Phase 1: Analyze the project (evidence, not assumption)

Gather, in parallel where possible:
- **Stack & tooling** — read `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `*.csproj` etc. Identify: language(s), framework(s), package manager, test runner, lint/typecheck/build scripts, monorepo layout (workspaces/packages/apps).
- **Structure** — Glob the top 2–3 directory levels. Identify the architectural units (modules, services, packages, apps, layers) and how they're organized.
- **Existing conventions** — read any existing `CLAUDE.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`, ADRs, `docs/`, `.editorconfig`, lint config. Capture rules already written down.
- **External integrations** — grep for SDKs/clients (payment, auth, cloud, queue, search, LLM). Each external dependency is a candidate adapter boundary and a candidate Critical Path.
- **Data & security surface** — auth/session handling, multi-tenancy, money/points/credits, PII, migrations, webhooks. Each is a candidate Critical Path.
- **Production surfaces** — the operational facts the `production-reviewer` cites when production quality is asked for: the **test runner + coverage tool**, the **logging/observability stack** (logger, error tracker, metrics/tracing SDK), the **migration/schema tool** and whether migrations are reversible by convention, and any **perf / compliance / SLO budgets** stated in docs or `NORTH_STAR.md` — plus the **CI gates** from the bullet below. Record what the evidence shows; a repo with no CI, no migrations, or no stated budget has "none found" — never invent one. (These feed the Phase 7 *Production surfaces* block in `project-context.md`.)
- **Operability facts (for the runbook)** — how a stranger would *run and recover* this system: the **deploy command/path** and the **rollback path** (deploy scripts, CI deploy jobs, `Procfile` / `fly.toml` / `vercel.json` / `render.yaml` / `Dockerfile`), the **env-var / config inventory** (from `.env.example` or a config schema — names and *where each lives*, **never values**, golden rule 2), the **log / observability locations** (where errors and logs actually go), and the **backup + restore steps** (backup scripts/jobs, and any evidence a restore was ever tested). Record only what the evidence shows — "none found" where a fact is absent, never invented. These feed the Phase 7 `RUNBOOK.md` write; gather them once here so the runbook and the *Production surfaces* block don't become two drifting inventories.
- **CI** — read `.github/workflows/` (or other CI) for the gates the project already enforces.
- **Existing `.claude/` inventory** — catalog what is already there: every agent, skill, and command (name + one-line purpose from its frontmatter), and every hook wired in `settings.json` — including artifacts this pack did not ship (hand-made, or from another tool). Note per artifact: its job, whether it already names this repo's real files/rules, and what it overlaps with. This inventory drives Phase 6's reconcile step — you cannot respect what you haven't catalogued. (On a fresh install the inventory is just the pack's own shipped files — note them and move on; do not reconcile the pack against itself.)

For a large codebase, spawn **one read-only `Explore` agent** to sweep and return conclusions, then verify the key claims yourself.

Produce an internal findings summary: stack, units, integrations, the verification scripts (typecheck/lint/test/build), and a candidate Critical-Path list.

### Phase 2: Decide the Critical Paths (with the user)

A **Critical Path** is a class of change where a mistake is expensive and silent — money movement, tenant isolation, auth, data integrity, an external-system contract, a compliance constraint, a hard architectural boundary. For each candidate from Phase 1, decide: is it a Critical Path for *this* project? **Think hard here** — this is the single highest-leverage judgment in the whole setup: a missed path is a class of change that is never gated, in any phase, forever. Reason through what a mistake on each candidate would silently cost — and which candidates you *almost* proposed — before concluding.

Present your derived list to the user via `AskUserQuestion` (multi-select) — the options you present *are* your recommended set. The user's confirm is the **only** backstop on this judgment, so give them the evidence to catch a miss, not a bare list:

- **Cite each candidate.** Every option's one-line `description` names the Phase-1 file/dir/integration it derives from **and** why a mistake there is expensive *and silent* — e.g. *"`src/billing/*` + Stripe webhook — a silent double-charge ships green"*. Keep it to that one line: `AskUserQuestion` descriptions are size-limited, so make it tight, never a paragraph.
- **Show the near-misses.** In the question text, add a short **"Considered, not proposed"** line naming the candidates you rejected, one word of reason each — e.g. *"logging — not silent; feature flags — no blast radius"*. Keep the whole line brief; if there are many, name only the closest 2–3. This is the cheapest recall device there is, and the first thing crowded out under pressure — the user catches a dropped path only if shown what you set aside, so it earns its line.

Keep the proposed set to the genuinely high-leverage ones — 3–7 is typical. Let the user add/remove. Only ask this once; everything else you can infer.

**Thin input — degrade, do not invent.** If Phase 1 found little to go on (a tiny repo, a single script, no external integrations, no auth/money/tenancy surface), produce a **minimal** setup: keep the universal baseline guardrails, wire up only the generic `code-reviewer`/`security-reviewer` gates (they ship with the pack), and write a short `CLAUDE.md` that states the stack and commands honestly. Do **not** manufacture Critical Paths the evidence does not support, and never fall back to the reference project's hospitality concepts (vendor isolation, idempotency ledgers, PCI, Uber Direct) to fill space — they are examples, not a template to copy. When uncertain whether something is a Critical Path, ask in the Phase 2 question rather than assuming.

For each confirmed Critical Path, note: the rule (what must always/never happen), how to detect a violation in a diff (the reviewer's job), and whether a fast textual pattern can catch the common violation at write time (the guardrail's job).

### Phase 2.5: Draft the North Star (the project's one outcome)

`NORTH_STAR.md` at the repo root holds the single outcome this project exists to achieve. `/create-plan` and `/go` read it as a lightweight **alignment gate** — a feature that hits a Non-goal or doesn't advance the Goal/Current focus gets flagged before code is written. If the file is missing or still the template (placeholder comments, empty sections):

- **Draft it from evidence.** From Phase 1 (README, docs, the product's evident purpose) and the Critical Paths just confirmed, draft: a **Goal** (one or two concrete, outcome-focused sentences — not "build great software"), **Why it matters**, 3–5 observable **Success looks like** signals, hard **Constraints**, **Non-goals** (things that look related but are deliberately out of scope), and a **Current focus** (the nearest milestone).
- **Degrade, don't invent.** If Phase 1 gave too little to state the goal honestly, ask the user **one** plain-language question — "In one sentence, what does this project most need to be great at?" — and build from the answer. Never manufacture a goal to fill the section.
- **Merge, never clobber.** Preserve anything the user already wrote; weave the draft around it. Write `NORTH_STAR.md` and show it for a quick confirm.

This is high-leverage but low-friction: draft, surface for challenge, move on. Do not block the bootstrap on it.

### Phase 3: Generate the project CLAUDE.md

Write (or augment, if one exists — never blindly overwrite; merge and confirm) `CLAUDE.md` at the repo root, containing (keep the template's permanent header contract line — the italic honest-and-lean rule under the title):
- **What you are building** — one paragraph, from Phase 1.
- **Golden rules** — the universal nine-rule floor, identical in every project. A fresh-install `CLAUDE.md` (seeded from the pack skeleton) already carries them: keep them **verbatim** — never regenerate, reword, or drop them. If the existing block is an **older revision** (the canonical section below has rules it lacks), append the missing rules verbatim and touch nothing else in the block. If the existing `CLAUDE.md` lacks the section entirely (it predates the pack), insert this canonical section as-is:

  > ## Golden rules (any project — keep these even if you rewrite everything else)
  >
  > 1. **Read before you write.** Never edit a file you haven't read; never state a "fact" about the code you haven't verified in the code.
  > 2. **No secrets in code, commits, or logs.** Credentials live in env/config; a leaked secret is a rotate-everything incident.
  > 3. **Never destroy what you didn't create without explicit confirmation** — files, data, branches, running state. Deletion is the one mistake you can't iterate on.
  > 4. **Fix causes, not symptoms.** A change that silences an error without explaining it hides the bug instead of fixing it.
  > 5. **Match the codebase.** Existing conventions beat your preferences; a new dependency needs a reason the standard library can't answer.
  > 6. **Report honestly.** Failing tests, skipped steps, and half-done work are reported as exactly that — "done" is a claim the checks have to back.
  > 7. **Small, verifiable steps.** Prefer the change you can test over the big-bang you can't; if you can't verify it, say so.
  > 8. **Scale caution to blast radius.** Reading and analyzing are free — they change nothing. Edits and test runs are cheap — they're reversible. Pushing, publishing, sending anything outside the repo, and deleting what you didn't create (rule 3) are not: those wait for explicit confirmation, and if you catch yourself reaching for reasons one is *probably* fine, that reaching is the signal to stop and ask.
  > 9. **Current facts beat trained memory.** Library APIs, CLI flags, and config schemas are present-day facts: verify against the installed version (lockfile, type definitions, `--help`, official docs) before use — partial recognition from training is not current knowledge.
- **Non-negotiable rules** — the numbered list derived from the confirmed Critical Paths. Each rule is a sentence an agent can obey, with the *why* in a clause. A rule that merely restates a golden rule is dropped; a project-specific *sharpening* of one (e.g. golden "no secrets" → "Stripe keys only via `env.server.ts`") stays, phrased as the sharper rule.
- **Lessons** — the self-updating mistake log, seeded from the template (instruction line + empty list). If the existing `CLAUDE.md` already carries gotchas / pitfalls / lessons-learned content, fold it in here (dedup, one line each) rather than leaving two lists.
- **Commands** — the real install/dev/test/lint/typecheck/build commands discovered in Phase 1.
- **Where things live** — the architectural units and what each owns. Only what an agent needs to navigate — one line per unit, never a full tree.
- **Conventions** — language strictness, money/units, timestamps, commit style, dependency policy (ADR-required?), discovered from Phase 1.
- **Critical Paths → reviewer mapping** — a table: each Critical Path → the reviewer skill + reviewer agent that gates it (the ones you generate in Phases 4–6). State the N-gates rule: a change touching N Critical Paths passes N gates.
- **Definition of Done** — the gate sequence (entry checks clean → reviewer gates pass → acceptance criteria met), adapted to this project's scripts. Write the entry-gate line **ratchet-aware** (green — or, with a recorded `docs/progress/entry-baseline.md`, no new failures vs that baseline), unconditionally: the clause is inert until a baseline exists, and Phase 7 records one only when the tree is red.
- **Pause points** (optional) — a `Pause points:` line telling `/go` where it must stop for the person's approval (e.g. `Pause points: plan approval` or `before each phase`). Do not ask about this — default to omitting it; Phase 8's summary carries the note that tells people it exists (or they just ask `/go` to pause once, and it offers to record it). Same default for a `Checkpoints:` line (`Checkpoints: on` = an announced git snapshot before each build phase): omit it here — the build commands ask once at the first build in a git repo and record the answer.

**Every line must earn its place.** `CLAUDE.md` rides in every session's context; each low-value line dilutes the rules that matter. Target **≤ ~100 lines**: state each rule once, and move explanation to a skill or doc with a pointer. If you can't fit under the budget, that usually means a section is doing a skill's job.

If a `CLAUDE.md` already exists, preserve its **meaning** and weave the new sections in — but reconcile at the content level, exactly as Phase 6 does for artifacts: the same convention stated twice in two voices is a defect, not preservation. Merge duplicates into the sharper phrasing (keep the user's wording when both are equally sharp), and show the user a diff-style summary of what you would add, merge, and leave untouched — **and confirm before writing**, exactly as Phase 6 does.

**Monorepo option.** If Phase 1 found multiple workspaces with materially different conventions, offer **once**: keep the root `CLAUDE.md` to the shared floor (golden rules, shared commands, the reviewer map) and put each workspace's specifics in a nested `<workspace>/CLAUDE.md` — Claude Code loads a nested file only when working under that directory, so each session pays only for the rules it needs. Default to the single-file form if the person doesn't care.

### Phase 4: Generate guardrail rules

Append project-specific rules to `.claude/guardrails.rules.json` (keep the universal baseline). For each Critical Path with a textually-detectable common violation, write a rule (schema is documented at the top of `.claude/hooks/guardrails.js`):
- `block` for violations that are unambiguous and expensive (e.g. a regulated-data literal, a client-derived tenant id on a privileged route, a raw secret).
- `warn` for heuristic checks that have false positives (e.g. a query that looks tenant-unfiltered, float arithmetic near a money identifier, a provider type leaking past an adapter directory).

Keep each rule's `filePattern`/`bodyPattern` specific enough to avoid noise. Validate the JSON parses (`node -e "JSON.parse(require('fs').readFileSync('.claude/guardrails.rules.json'))"`).

### Phase 5: Generate post-edit checks

Populate `.claude/workspaces.json` from the real verification scripts found in Phase 1 — map each workspace/path to its typecheck/lint/build command, ordered specific-before-broad. Add note-only entries for discipline reminders (e.g. "model changed — regenerate the migration"). Start conservative: a failing check blocks the edit loop, so only wire commands that are fast and reliable. On a repo that is red today, wire only the commands that are green now (or note-only entries) — a permanently-red blocking check fights every edit; leave the red checks to the entry gate's baseline ratchet (Phase 7). Validate the JSON parses.

### Phase 6: Generate reviewer agents + Critical-Path skills

**Reconcile before you generate (one artifact per job).** For each artifact you are about to create, check the Phase 1 inventory for an existing agent/skill/command that already does that job — match by *purpose*, not filename:

- **Exists and already tailored** (names this repo's real files/rules — whoever wrote it) → keep it and register it in the Critical-Path table instead of generating a duplicate. Two artifacts for one job is worse than one imperfect artifact.
- **Exists but generic or outdated** → **upgrade in place**: keep the existing file's project-specific knowledge (paths, rules, exceptions someone hand-added — that tailoring is the most valuable content in the file), add what it lacks from the pack's current shape (the Readiness headline, evidence discipline, read-only tools). Show the diff and confirm before writing — an existing file is never silently overwritten, same rule as the installer.
- **Conflicts** (an existing artifact contradicts a confirmed Critical Path, or two artifacts answer the same question differently) → surface it as a decision with your recommendation; never pick silently.
- **Redundant copies** (two existing artifacts doing the same job) → propose keeping the better one — judged by which is more project-specific and more current — and retiring the other, one-line reason each. Retiring means asking first: delete only after the user explicitly confirms, never silently.

**Scope of reconcile:** the pack's own shipped commands/skills/agents are **not** upgrade targets — `/sync-pack` owns pack-version upgrades; this command leaves shipped files untouched. Reconcile only hand-made, foreign, or previously *generated* artifacts.

For each confirmed Critical Path, generate a matched pair (model them on the pack's generic `code-reviewer.md` / `security-reviewer.md`):
- **`.claude/agents/<path>-reviewer.md`** — a read-only reviewer agent (`tools: Read, Grep, Glob, Bash`) with: a precise `description` (so it's selectable), numbered checks specific to this project's rule, an output shape with `path:line` evidence, and a `PASS / NEEDS CHANGES / BLOCK` verdict **led by the same Readiness headline the generic reviewers use** (`Readiness: Ready | Almost | Not yet · Grade: A–F · <one plain sentence>`, derived from the findings so any BLOCK is "Not yet"). Copy the headline convention, the standing footer (the template's last line: "Ask `/go` to explain any finding…"), and the verdict disciplines (assume defects exist; rule alternatives out, don't confirm the favorite) from `code-reviewer.md` so every gate reads and judges the same. Name the exact files/tables/routes the rule governs in *this* repo. **Concentrate the strongest model at the gates:** if the account exposes a model stronger than the session default, pin it in each reviewer's frontmatter (`model: <that model>`) — the pack's quality lives at its reviewer gates, so reviewers earn the strongest model even when implementers run on the default. (Ask the user once which models their account exposes; never guess a model id. If they don't know or don't care, skip pinning — the session default is fine.) **Also pin `effort: max` in each generated reviewer's frontmatter, unconditionally** — the gates think hardest. Unlike `model:`, `max` is the ceiling on any model (it never downgrades a stronger session) and needs no per-account ask. It applies when the reviewer is dispatched **by name**; under a consolidated/lean run the `"think hard"` brief carries the effort instead (there is no per-dispatch effort override).
- **`.claude/skills/<path>/SKILL.md`** — the rule canon the reviewer enforces, with frontmatter `name` + a `description` that triggers on the relevant keywords. This is what `/create-plan` and `/implement` invoke before writing code on that path.

Also generate the project's **specialist implementer agents** if the project warrants a team (e.g. a backend agent, a frontend agent, a test agent) — each a focused agent with a precise `description`, this project's stack and conventions pinned in its body, and only the tools it needs. **Pin `effort: high`** (not `max`) in each implementer's frontmatter — producers ship better at high; `max` over-thinks and over-engineers. Leave `model:` to inherit the session; only the gates earn a pinned model. Only generate the ones that map to real surfaces in the repo.

Generate a **project command** only when Phase 1 found a repeated, multi-step, project-specific workflow the shipped commands don't cover (a domain-specific deploy/reset/report flow an agent gets asked for again and again). Default is **none** — commands are the surface a person has to learn, so every added one must earn its place.

> This is the *initial* skill set, from the repo as it is today. Repos grow new Critical Paths later; `/sync-pack` re-prospects for newly-warranted skills using the `discovering-project-skills` skill, so the coverage keeps pace without re-running bootstrap.

### Phase 7: Wire and verify

- **Confirm the hooks are actually wired.** The installer copies `settings.json` only when none existed; if the project already had one, the pack's settings landed as `.claude/settings.pack.json` and the hooks are **not** active yet. Check: does the live `.claude/settings.json` contain `PreToolUse → guardrails.js` and `PostToolUse → post-edit-check.js`? If a `settings.pack.json` exists or the hooks are absent, **merge the pack's `hooks` block (and any missing `permissions`) into the live `settings.json`** (show the user the diff first), then delete `settings.pack.json`. Merge means **append alongside, never replace**: any hook another tool wired (a formatter, a different pack, a hand-written check) stays exactly where it is — the pack's hooks are added as additional entries, and if the same event+matcher already runs a foreign hook, both run. Do not blindly overwrite the user's existing settings.
- Confirm the permission `allow` list covers the project's real commands (typecheck/lint/test/build) — suggest additions for the user to approve. Note whether `permissions.defaultMode` is `plan` and confirm that matches what the user wants for this repo.
- Run a smoke test: pipe a crafted PreToolUse payload into `node .claude/hooks/guardrails.js` to confirm a block rule fires (exit 2) and the rule JSON loads; run one `workspaces.json` check command manually to confirm it's green on the current tree (Phase 5 wires only currently-green commands, so red here means a wiring mistake, not the brownfield state).
- **Capture the brownfield baseline (only if the tree is red).** Run the discovered typecheck/lint/test once. All green → nothing to record. Any red → write `docs/progress/entry-baseline.md`: date, commit (if a git repo), and per check the failing **count and the failing identifiers** the runner reports (test names, error file:lines) — identifiers, not bare counts, so "fixed one, broke one" can't pass as no-change. From then on every entry gate passes on *"green, or no new failures vs this baseline"*: the baseline only ever ratchets **down** (each improving run rewrites it to the smaller set), and the first all-green run deletes it — "no worse" is an improvement curve toward green, never the permanent standard. If the project has **no test runner at all**, don't invent a baseline — note it for the Phase 8 summary and offer scaffolding a minimal one as phase 0 of the first plan.
- If the project has a UI surface, check whether a browser/screenshot tool is available to Claude (a Playwright or browser-devtools MCP, a `browse` skill). If not, recommend wiring one in the Phase 8 summary — `/design`'s render-and-iterate loop depends on it, and seeing the rendered UI is the single biggest lever on UI quality.
- Check whether the **Codex CLI** is installed and authenticated (run the probe from `.claude/codex-review.md`). Without it, the cross-model check in the build gates and `/audit`'s outside voice skip silently — and cross-model agreement is the strongest signal the audit produces. If absent, recommend installing and authenticating it in the Phase 8 summary; never block on it.
- Write `.claude/project-context.md` — the longer-form context bible the orchestration commands read: stack, units, Critical Paths, the reviewer/skill inventory, and the discovered command list. Include a **Production surfaces** block from the Phase 1 discovery — the real **test + coverage command**, the **logging/observability convention** (where errors go, at what level), the **CI gates** actually enforced, the **migration tool + reversibility rule**, and any **perf / compliance / SLO budgets** (each cited to its evidence file, or an explicit "none found"). This is the block the on-demand `production-reviewer` reads so its findings name *this repo's* real commands and conventions instead of generic advice. Degrade honestly: record only what the evidence supports — a repo with no CI or no migrations says so; never manufacture a surface to fill the section.
- Write `RUNBOOK.md` at the repo root — the operating manual for a stranger (or the founder six months later), from the Phase 1 **Operability facts** (reuse that gather; do not run a second one). Sections, each drawn from real evidence or an explicit "none found — <the gap to close>": **Deploy** (how a change goes live), **Rollback** (how to undo a bad deploy — name it *before* it's needed), **Configuration** (the env-var / config inventory: each name and *where it lives* — the secret store, the `.env` key — **never a value**, golden rule 2), **Observability** (where logs and errors go when something breaks), and **Backup & restore** (where the durable data lives, how it's backed up, and — stated plainly — whether a restore has ever been tested and when one last succeeded; if unknown, write "restore never tested" rather than implying safety). This is the artifact the `operability-critic` audits (the stranger test). Merge, never clobber: if a `RUNBOOK.md` already exists, weave the discovered facts in and confirm, exactly as with `CLAUDE.md`. On a repo too thin to fill it (a tiny script, no deploy surface), write a short honest stub naming what's absent — don't manufacture an operations story the repo doesn't have.

### Phase 8: Summary

Report: the Critical Paths confirmed, every file created/modified (CLAUDE.md, NORTH_STAR.md, guardrail rules, workspaces.json, each reviewer agent, each skill, project-context.md — including its *Production surfaces* block, so the person knows the on-demand production gate now cites this repo's real commands, and RUNBOOK.md — the stranger-test operating manual the `operability-critic` audits, noting plainly if the backup/restore section says a restore was never tested), the smoke-test results, the brownfield baseline if one was recorded (say plainly: the checks start red, so the gates hold the line at "no new failures" and tighten toward green as fixes land — or, if there is no test runner at all, offer scaffolding a minimal one as phase 0 of the first plan), the suggested `settings.json` permission additions, and a one-line note that adding a `Pause points:` line to `CLAUDE.md` makes `/go` stop for approval at named checkpoints (e.g. plan approval), that the first build will offer once to turn on per-phase git snapshots (a `Checkpoints:` line — an announced restore point before each phase), and that the pack keeps two repo-root memory ledgers, both **created on first entry** (see the `using-the-pack` skill): a **decision journal** (`DECISIONS.md`) — `/shape`, `/create-plan`, and `/go` offer to log a load-bearing decision when one is settled and read it back so a settled question isn't reargued — and a **feedback ledger** (`FEEDBACK.md`) — `/go`, `/shape`, and `/triage` offer to capture what a user asks for, and `/go` with no goal ranks those asks against `NORTH_STAR.md` to answer "what should I build next?". For a UI project with no browser/screenshot tool wired, include the Phase 7 recommendation to add one; if the Codex CLI was missing, include the recommendation to install and authenticate it so the cross-model checks stop skipping. Tell the user the setup is ready and that the simplest next step is just `/go <what you want to build>` — it will plan, build, and review for them — or, to drive each step manually, `/create-plan <first-feature>`.

## Rules
- **Derive, never transplant.** Do not import the reference project's hospitality rules into a non-hospitality project. Every rule must trace to evidence in *this* repo or an explicit user decision.
- **Merge, never clobber.** An existing `CLAUDE.md` or config is augmented and confirmed, not overwritten.
- **Reconcile, never duplicate.** One artifact per job: prefer upgrading an existing agent/skill/command over generating a parallel one; when upgrading, preserve the project-specific tailoring someone already put in. Retire redundant copies only with the user's confirmation, and never silently overwrite or delete anything you didn't just create.
- **Validate generated config.** Every JSON file you write must parse; every guardrail regex must compile (the engine skips invalid ones, but you should not ship them).
- **Ask once for scope, always before touching what exists.** The only mandatory *scoping* interaction is confirming the Critical-Path set (Phase 2) — but never upgrade, overwrite, or retire an existing artifact without confirmation; those asks are mandatory too. Surface everything else in the summary for challenge rather than blocking on it.
