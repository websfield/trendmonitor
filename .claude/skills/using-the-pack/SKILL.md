# Using claude-jig

This project has claude-jig installed. claude-jig is **machinery + a generator**: generic orchestration commands and hook engines, plus `/bootstrap-claude-pack` which tailors everything to this repo. The simplest way to use all of it is **`/go`** — it drives the rest for you.

## The pieces

| Piece | What it is | Where |
|---|---|---|
| `/go` | **Start here.** The plain-language front door: say what you want and it runs the right step (set up → plan → build → check) from wherever the project is, pausing only for real decisions. Drives the commands below so the person needn't know them. | `.claude/commands/` |
| `/bootstrap-claude-pack` | Analyzes this repo and generates the tailored setup (CLAUDE.md, North Star draft, guardrail rules, reviewer agents, Critical-Path skills). Run once per project. | `.claude/commands/` |
| `/shape` | **Founder mode.** Before planning, pressure-tests whether you're building the right thing — finds the real job hiding in the request, aligns it to the North Star, writes a brief the next step reads (small clear asks ride `/implement`'s fast lane; everything else goes to `/create-plan`). Proportional: small clear asks pass straight through. | `.claude/commands/` |
| `/create-plan` | Turns a feature request (and the shaping brief) into a master plan + phase plans with conventions pinned, gated by a multi-agent plan review. | `.claude/commands/` |
| `/start-teams` | Implements a plan by spawning specialist agents, gating each phase through reviewers + the Definition of Done. | `.claude/commands/` |
| `/implement` | Implements a plan yourself (no team), same gates. For smaller plans. Its **fast lane** ships a small, clear change (a brief that names its exact surface) with **no plan documents at all** — same gates: entry checks, every touched Critical-Path reviewer, the Definition of Done, and a short report card. | `.claude/commands/` |
| `/triage` | **Support-to-fix.** Paste a bug report or customer email: it reproduces the issue against the real code, fixes it through `/implement`'s fast lane (every gate, no plan paperwork), and **drafts — never sends** — the customer reply, with every claim traced to the verified fix. The pack as your support engineer. For a *live outage* (down right now), that's `/incident`, not this. | `.claude/commands/` |
| `/incident` | **The prod-down firefight.** For when the site is down / users are locked out / payments are failing *right now*: **stabilize first** (offer the rollback/mitigation from `RUNBOOK.md` before any root-causing, one fast confirmation, golden rule 8), then diagnose ("what shipped last?"), fix through `/implement`'s fast lane (every touched gate still runs), and write a short **postmortem to memory** (Lessons / a guardrail rule / a RUNBOOK gap). Distinct from `/triage` (normal-temperature bug) — this handles the fire. | `.claude/commands/` |
| `/review-phase` | Independently verifies a shipped phase against its Acceptance Criteria + reviewer gates; reports a plain-language **report card** (Ready / Almost / Not yet). | `.claude/commands/` |
| `/release` | **The act-of-shipping gate.** After the code is judged *ready* (production-reviewer / phase reviews), makes the *release itself* disciplined: a plain-language changelog from the ledgers, a migration/env checklist, a **rollback plan named before the deploy** (pulled from `RUNBOOK.md`), and a post-deploy smoke test — then a report card. Never deploys, migrates, commits, tags, or pushes on its own (golden rule 8). Not for a live outage — that's `/incident` (stabilize first). | `.claude/commands/` |
| `/design` | **UI/UX front door.** Establishes a project `DESIGN.md`, grounds the look in references or an aesthetic family, renders 2–3 directions you pick with your eyes, and iterates on screenshots so the UI isn't a generic AI default; routes to the right tool when generation helps (Stitch / Claude Design / Canva / OpenAI image) and verifies (accessibility, states, looks). Drives the `designing-uis` + `ui-design-tools` skills. | `.claude/commands/` |
| `/sync-docs` | **Technical-writer mode.** Makes the docs match the shipped code — auto-fixes mechanical drift (paths, lists, counts, trees), asks before subjective rewrites, never invents capabilities. | `.claude/commands/` |
| `/doctor` | **Health check.** On-demand, read-only: is Node present and is the hook safety layer (guardrails / post-edit / session-start) actually wired and live? Re-runnable any time — the counterpart to the installer's one-time Node check for when things change later. Reports a Ready / Almost / Not yet card with the one fix that matters. | `.claude/commands/` |
| `/bootstrap-critics` + `/audit` | **Audit mode** (whole-codebase, not a per-change gate). `/bootstrap-critics` generates this repo's read-only **critic panel** — one auditor per real lens (architecture, security, ops, ux, …), tagged by track; four generic critics ship (`architecture-critic`, `accessibility-critic`, `correctness-critic`, and `operability-critic` — the **stranger test**: could someone who didn't build this run and *recover* it from the docs, with the backup/restore reality check). `/audit` (or `/audit <track>`) convenes them and merges their findings into one ranked, owner-assignable **risk register** (`docs/progress/audit/<date>.md`), led by the same Ready / Almost / Not yet report card. Run periodically — before a milestone, when inheriting a system, or when hardening one. `/interrogate <path>` deep-reads a single file with full attention (the depth counterpart to the audit's breadth) and, if an audit register exists, logs anything the last audit missed to its escape list. See the `auditing-with-critics` skill for the audit-vs-gate distinction. | `.claude/commands/` |
| Guardrail hook | PreToolUse engine reading `.claude/guardrails.rules.json` — blocks/warns on risky writes. | `.claude/hooks/guardrails.js` |
| Post-edit hook | PostToolUse engine reading `.claude/workspaces.json` — runs typecheck/lint on the changed area. | `.claude/hooks/post-edit-check.js` |
| Session-start hook | Read-only orientation — prints the pack status + recommended next step when a session starts, so anyone knows what to do. Fail-open; never blocks. | `.claude/hooks/session-start.js` |
| North Star | `NORTH_STAR.md` at the repo root — the one outcome the project exists for. `/create-plan` and `/go` read it to flag scope creep (a Non-goal, or work that doesn't advance the Goal) before code is written. | repo root |
| Runbook | `RUNBOOK.md` at the repo root — the stranger-test operating manual `/bootstrap-claude-pack` writes: deploy, rollback, config inventory (locations, never values), observability, and the backup + restore reality check. The `operability-critic` audits it; degrades honestly when a fact is "none found". | repo root |
| Reviewer agents | Read-only gate agents (generic + project-specific). `code-reviewer` and `security-reviewer` run on touched Critical Paths; `simplification-reviewer` is an **advisory** over-engineering gate (what to delete/replace with stdlib/native) that judges means not coverage and can never reduce the Definition of Done; `production-reviewer` is an **on-demand** production-readiness gate that runs only when you ask for production quality ("ship to prod", "make this production-ready") or `CLAUDE.md` / `NORTH_STAR.md` declares a production target. | `.claude/agents/` |
| `keeping-it-lean` skill + `/shortcut-ledger` | The leanness canon: the economy-of-means ladder (reuse → stdlib → native → one line) and the `SHORTCUT:` marker convention. `/shortcut-ledger` harvests those markers into a ledger. Economy governs *how* you build, never *how much* you cover. | `.claude/skills/`, `.claude/commands/` |

## The workflow

```
the easy way:       /go <what you want>      (figures out the rest, from any starting point)

drive it yourself:
  new project:      /bootstrap-claude-pack   (once)
  each feature:     /shape <feature>  →  /create-plan <feature>  →  /start-teams <feature>  (or /implement)
  small fix:        /shape <fix>  →  fast lane (/implement, no plan docs)  →  report card
  bug report:       /triage <paste the report>  →  reproduce  →  fast-lane fix  →  draft (never send) the reply
  prod is DOWN:     /incident <what's broken>   →  stabilize first (rollback)  →  diagnose  →  fast-lane fix  →  postmortem
  verify a phase:   /review-phase <feature> <N>
  ship a release:   /release            (changelog + migration/env checklist + rollback-before-deploy + smoke test — after the code is Ready)
  keep docs honest: /sync-docs
  audit the system: /bootstrap-critics  (once)  →  /audit  (periodically)  ·  /interrogate <file>  (grill one file)
  check the pack:   /doctor                  (is Node present + the hook safety layer live?)
```

`/go` is a convenience over the same machinery, not a shortcut around it: it runs the same
guardrails, reviewer gates, and Definition of Done. It lowers the bar to *start*, never to *ship*.

## How to behave in this project

1. **Read `CLAUDE.md` and `.claude/project-context.md`** before non-trivial work — they hold this project's golden rules (universal), non-negotiable rules (project-specific), the **Lessons** mistake log (rules distilled from mistakes that actually happened here — obey them; they exist because something already went wrong once), and the Critical-Path → reviewer mapping. They override generic habits.
2. **A change touching N Critical Paths passes N reviewer gates.** Never skip a gate because a change is small or tests pass.
3. **Entry gate before reviewer gates.** typecheck/lint/test must be clean before any reviewer renders a verdict — green, or (when a baseline is recorded at `docs/progress/entry-baseline.md`) no **new** failures vs it; the baseline only ratchets down and retires at green. Reviewers read code, they don't run it.
4. **If `CLAUDE.md` is missing or thin**, the project isn't set up yet — recommend `/go` (it sets up first, then continues) or `/bootstrap-claude-pack`. The orchestration commands depend on the project contract existing.
5. **If the person seems unsure what to do, point them at `/go`.** They never need to learn the individual command names; `/go` reads the project's state and does the right next thing.
6. **Respect the North Star, and shape before you plan.** If `NORTH_STAR.md` is filled, a feature that hits a Non-goal or doesn't advance the Goal is flagged before planning. For anything vague or ambitious, `/shape` first — make sure you're building the *right* thing — but never inflate a small, clear ask into something bigger; the person decides the scope.
7. **Report gate results as a report card.** Reviewers and `/review-phase` lead with a plain-language readiness line (Ready / Almost / Not yet) earned by the findings, so a non-expert can read the result. The grade follows the findings — a blocker is always "Not yet"; never inflate it.
8. **The guardrail hook is defense in depth.** If it blocks a write, fix the design — don't route around it. If a rule is wrong for this repo, edit `.claude/guardrails.rules.json`, don't disable the engine.
9. **A phase gates on proof, not on a table cell.** A phase is startable only when every phase it *Depends on* is proven complete **on disk** — its Ready phase-review (the flat file `docs/progress/<feature>-phase-<N>-review.md`), or its entry-gate + Definition-of-Done evidence under the `docs/progress/<feature>/` directory. A `Complete` row in the master plan is a *claim*, not the proof, so a stale or hand-edited table can never let a phase start on unfinished work; a missing proof defaults to blocked. The orchestrators (`/start-teams`, `/implement`) record each step in an append-only **progress ledger** (`docs/progress/<feature>/ledger.md`) — the timeline that makes a session resumable and the report card reconstructable after an interruption. The ledger is a convenience layer, not the source of truth: proof is the evidence, so a missing or garbled ledger never blocks work.
10. **Undo has two layers.** Claude Code natively checkpoints Claude's own file edits on every prompt — `/rewind` restores them, but it does **not** cover what shell commands, codegen, or migrations change. For that wider blast radius, a `Checkpoints: on` line in `CLAUDE.md` (offered once at the first build in a git repo, never assumed) makes the build commands save an **announced** git snapshot before each phase — canonical mechanics in `implement.md` Step 2. Both are safety nets, not a git policy change: nothing is committed, stashed, or dropped without a recorded ask.
11. **Spawned subagents inherit no session context.** The session-start orientation and your `CLAUDE.md` reach the main thread, not Task-spawned agents — Claude Code does not propagate SessionStart output or auto-read `CLAUDE.md` into a subagent. So every convention a reviewer or specialist must honor is pinned **verbatim into its spawn prompt** (`/start-teams` 2b, `/review-phase` Step 4); the phase plan is the single contract. (A `SubagentStart` hook *could* inject shared context automatically; the pack keeps it explicit-in-the-prompt instead — one auditable contract, no hidden hook state. That hook is the lever if you ever want always-on subagent guidance.)
12. **Record load-bearing decisions — the decision journal (`DECISIONS.md`).** A team of one has no one to remember *why* a choice was made; six months later the founder is a stranger to their own trade-offs. `DECISIONS.md` at the repo root is that memory — **one line per settled decision**: `- YYYY-MM-DD — <what was decided> — because <why>` (a pointer to the plan/brief when relevant, never a copy of it). This is the **canonical definition** of the convention; the commands below just point here. Two disciplines keep it worth reading, both borrowed from **Lessons**: it is **always offered, never silent** — a person okays every entry — and it is **capped to load-bearing decisions** (a chosen scope, a plan-review trade-off, an accepted risk, an overridden reviewer BLOCK), never every micro-choice. The commands that *make* a decision offer to append at the moment it happens — `/shape` on the chosen scope, `/create-plan` on a settled trade-off, `/go` on an overridden BLOCK or an accepted audit-register risk — and the commands that *plan* (`/shape`, `/create-plan`, `/go`) **read it first when it exists**, so a question settled last month isn't relitigated from scratch — and a request that would *reverse* a load-bearing decision is surfaced for the person to weigh, never silently overturned. The file is **created on first entry** — nothing ships empty, and an absent journal simply means the reading step finds nothing and moves on.

13. **Capture what users ask for — the feedback ledger (`FEEDBACK.md`).** "What should I build next?" is the one-person company's daily decision tax, and the answer lives in what users actually ask for — which is exactly what a solo founder, heads-down building, forgets by next week. `FEEDBACK.md` at the repo root is that memory — **one line per user ask or complaint**: `- YYYY-MM-DD — <what a user asked for / complained about> — <source>` (the source is the *channel* it came from — a support email, a chat, an app-store review — never the person's name, address, or account details). This is the **canonical definition** of the convention; the commands below just point here. Two disciplines, both borrowed from the decision journal above: it is **always offered, never silent** — a person okays every entry — and it is **capped to real user signal** (a genuine ask or complaint from someone using the product), never every idea the founder has in the shower. **Unlike the decision journal, this ledger is a backlog that gets fulfilled** — a decision never closes, but an ask does. So it has one bit of lifecycle: **when an ask ships, mark its line `— done` (or delete it)**, and the "what's next" ranking below reads only the **open** asks (the unmarked lines) — otherwise it would keep re-recommending things already built. (This is also what separates it from **Lessons**: a Lesson asks "how do we not repeat our own mistake?"; feedback asks "what do users want next?" — an outside signal, not our own error.) The commands that might *hear* a user signal offer to append at the moment it surfaces — `/go` and `/shape` when the person mentions an ask they're not building now, `/triage` when a customer report carries a feature request alongside the bug — and the commands that *decide what's next* read it: **`/shape`** reads it as real-job evidence (a request echoing a recurring ask is a stronger signal; related asks reveal the bigger job), and **`/go`'s empty-argument mode** (`/go` with no goal) **ranks the open asks against `NORTH_STAR.md`** — which one most advances the Goal / Current focus — to answer "what should I build next?" with evidence instead of a guess. It **offers** the top pick, never launches a build unasked; with no filled North Star to rank against it lists the asks unranked instead. The file is **created on first entry** — an absent ledger just means the reading step finds nothing and the pack works exactly as before.

## Running on a weaker session model (dials, not a mandate)

The pack works on any model — none of this is a requirement to buy the most expensive tier. These are **dials** that close most of the gap when your session model isn't the strongest the account exposes. The pack concentrates its quality at the gates, so a little asymmetry goes a long way; half of the leverage is operator behavior no command can enforce for you.

1. **Seat the strongest model at the gates.** Put the best model the account exposes on the main session and on **every** reviewer gate and critic; implementers may drop a tier, never the reverse. Reviewer and critic agents take a `model:` field at the top of each agent file (`.claude/agents/`) — that is where a stronger model pays for itself, because that is where "done" is decided. (The main-session model is the one you pick when you launch Claude Code.) The pack also ships every gate agent with **`effort: max`** frontmatter — the gates reason at full intensity on whatever model runs them (`max` is the ceiling on any model, so it never downgrades a stronger session and needs no per-account tuning), while generated implementers default to **`effort: high`** (producers over-engineer at `max`). Two caveats keep this honest:
   - **By-name only.** `effort: max` applies when a gate is dispatched **by name** — a full-intensity review, or `/audit`. Under a **lean** consolidated run (dial 6) or a `general-purpose` fallback, the frontmatter can't ride along and there's no per-dispatch effort override, so the `"think hard"` brief carries the effort instead.
   - **Not retroactive.** A fresh install carries it from the start; an *existing* project gets it only after `/sync-pack` (shipped gates) or a re-bootstrap (generated ones).
2. **Keep Codex** — the pack's independent second-model reviewer — **authenticated** (`.claude/codex-review.md`) so the cross-model check never silently skips. A second model is the cheapest stand-in for a stronger one, and cross-model agreement is the strongest signal the gates produce.
3. **One phase per session, then `/clear`.** Long sessions drift; the progress ledger and the session-start re-orientation are the drift defense — lean on them rather than pushing one session through many phases.
4. **Spend thinking at the un-gated judgment moments** — bootstrap's Critical-Path derivation, an ambiguous `/go` route, audit synthesis. These main-loop passes have no reviewer behind them, so one wrong call shapes everything downstream; say **"think hard"** before the step to raise the budget exactly where a miss would be silent.
5. **Budget for extra review rounds.** More "Almost / Not yet" rounds are the *expected* cost of a smaller model, not a sign of failure — the gates are built to cap each review at two rounds and then surface anything still unresolved, so the extra rounds are already accounted for. Never trim a gate to save a round; that trades a visible round for a silent miss.
6. **On a limited plan, set the dial — don't improvise skips.** A `Gate intensity: lean` line in `CLAUDE.md` consolidates each reviewer gate into **one merged reviewer run** that still renders a verdict per touched Critical Path — never zero reviewers, never fewer checklists; the only thing dropped is the advisory simplification pass — which was never a gate — and every lean run is announced on the report card. Reach for the other dials first (one phase per session, Codex authenticated); lean trades parallel specialist eyes for one consolidated pass — sanctioned and visible, where an improvised gate skip is silent drift.
