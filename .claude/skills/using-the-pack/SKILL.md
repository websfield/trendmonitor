# Using claude-jig

This project has claude-jig installed. claude-jig is **machinery + a generator**: generic orchestration commands and hook engines, plus `/bootstrap-claude-pack` which tailors everything to this repo. The simplest way to use all of it is **`/go`** — it drives the rest for you.

## The pieces

| Piece | What it is | Where |
|---|---|---|
| `/go` | **Start here.** The plain-language front door: say what you want and it runs the right step (set up → plan → build → check) from wherever the project is, pausing only for real decisions. Drives the commands below so the person needn't know them. | `.claude/commands/` |
| `/bootstrap-claude-pack` | Analyzes this repo and generates the tailored setup (CLAUDE.md, North Star draft, guardrail rules, reviewer agents, Critical-Path skills). Run once per project. | `.claude/commands/` |
| `/shape` | **Founder mode.** Before planning, pressure-tests whether you're building the right thing — finds the real job hiding in the request, aligns it to the North Star, writes a brief the next step reads (small clear asks ride `/implement`'s fast lane; everything else goes to `/create-plan`). Proportional: small clear asks pass straight through. | `.claude/commands/` |
| `/create-plan` | Turns a feature request (and the shaping brief) into a master plan + short six-section phase plans (≤10 files each), gated by one `plan-reviewer` round. | `.claude/commands/` |
| `/start-teams` | Implements a plan by spawning specialist agents — when a phase's *Files* Owner column names two or more different specialists — gating each phase through reviewers + the Definition of Done. | `.claude/commands/` |
| `/implement` | Implements a plan yourself (no team), same gates — the default build lane. Its **fast lane** ships a small, clear change (a brief that names its exact surface) with **no plan documents at all** — same gates: validation, every touched Critical-Path reviewer, the Definition of Done, and the 8-row report card. | `.claude/commands/` |
| `/triage` | **Support-to-fix.** Paste a bug report or customer email: it reproduces the issue against the real code, fixes it through `/implement`'s fast lane (every gate, no plan paperwork), and **drafts — never sends** — the customer reply, with every claim traced to the verified fix. The pack as your support engineer. For a *live outage* (down right now), that's `/incident`, not this. | `.claude/commands/` |
| `/incident` | **The prod-down firefight.** For when the site is down / users are locked out / payments are failing *right now*: **stabilize first** (offer the rollback/mitigation from `RUNBOOK.md` before any root-causing, one fast confirmation, golden rule 8), then diagnose ("what shipped last?"), fix through `/implement`'s fast lane (every touched gate still runs), and write a short **postmortem to memory** (Lessons / a guardrail rule / a RUNBOOK gap). Distinct from `/triage` (normal-temperature bug) — this handles the fire. | `.claude/commands/` |
| `/review-phase` | Independently verifies a shipped phase against its acceptance criteria + reviewer gates; writes the plain-language **report card** (Ready / Almost / Not yet) into the feature's record. | `.claude/commands/` |
| `/release` | **The act-of-shipping gate.** After the code is judged *ready* (production-reviewer / phase reviews), makes the *release itself* disciplined: a plain-language changelog from the ledgers, a migration/env checklist, a **rollback plan named before the deploy** (pulled from `RUNBOOK.md`), and a post-deploy smoke test — then a report card. Never deploys, migrates, commits, tags, or pushes on its own (golden rule 8). Not for a live outage — that's `/incident` (stabilize first). | `.claude/commands/` |
| `/design` | **UI/UX front door.** Establishes a project `DESIGN.md`, grounds the look in references or an aesthetic family, renders 2–3 directions you pick with your eyes, and iterates on screenshots so the UI isn't a generic AI default; routes to the right tool when generation helps (Stitch / Claude Design / Canva / OpenAI image) and verifies (accessibility, states, looks). Drives the `designing-uis` + `ui-design-tools` skills; browser proof follows `verifying-webapps` (reuse the project's harness, assert not sleep, one evidence line per check, `unverified` when there is none). | `.claude/commands/` |
| `/sync-docs` | **Technical-writer mode.** Makes the docs match the shipped code — auto-fixes mechanical drift (paths, lists, counts, trees), asks before subjective rewrites, never invents capabilities. | `.claude/commands/` |
| `/user-docs` | **The docs your users read.** Generates and maintains customer-facing help under `docs/help/` (getting-started, per-feature how-tos, FAQ) — derived from what actually shipped, written for a reader who has never seen the repo, and gated by the `outbound-truth` skill so the help can never promise what the product doesn't do. Re-run after features ship: new pages offered, changed pages flagged, removed features retire-offered. Never publishes anywhere. | `.claude/commands/` |
| `/recap` | **The weekly founder brief.** Come back after days away and get one page assembled from the records the pack already keeps: **shipped** (the records' `complete` lines and Ready cards, plus git-log work outside the records — named honestly), **stuck** (blocked phases, Almost/Not-yet cards, a red baseline, open audit items), **decided & heard** (`DECISIONS.md` + open `FEEDBACK.md` asks), and **the one thing next** (reusing `/go`'s own ranking — offered, never launched). Read-only; offers to save to `docs/progress/recap/<date>.md`, which becomes the next recap's window marker. | `.claude/commands/` |
| `/doctor` | **Health check.** On-demand, read-only: inspect Node availability, configured hook entries, config parsing, and direct engine probes. Reports a Ready / Almost / Not yet card scoped to those checks, with one next action. Host dispatch remains unknown without host evidence; a sidecar or silent startup cannot establish it. An informational footnote lists configured model requests, not proof of which models ran. Re-runnable any time; `/go` guides missing setup. | `.claude/commands/` |
| `/bootstrap-critics` + `/audit` | **Audit mode** (whole-codebase, not a per-change gate). `/bootstrap-critics` generates this repo's read-only **critic panel** — one auditor per real lens (architecture, security, ops, ux, …), tagged by track; six generic critics ship: `architecture-critic`, `accessibility-critic`, `correctness-critic`, `operability-critic` (the **stranger test**: could someone who didn't build this run and *recover* it from the docs, with the backup/restore reality check), `outbound-truth-critic` (do the claims customers read trace to what shipped?), and `supply-chain-critic` (is anything watching the dependencies and the license floor?). `/audit` (or `/audit <track>`) convenes them and merges their findings into one ranked, owner-assignable **risk register** (`docs/progress/audit/<date>.md`), led by the same Ready / Almost / Not yet report card. Run periodically — before a milestone, when inheriting a system, or when hardening one. `/interrogate <path>` deep-reads a single file with full attention (the depth counterpart to the audit's breadth) and, if an audit register exists, logs anything the last audit missed to its escape list. See the `auditing-with-critics` skill for the audit-vs-gate distinction. | `.claude/commands/` |
| Guardrail hook | PreToolUse engine reading `.claude/guardrails.rules.json` — blocks/warns on risky writes. | `.claude/hooks/guardrails.js` |
| Post-edit hook | PostToolUse engine reading `.claude/workspaces.json` — runs typecheck/lint on the changed area. | `.claude/hooks/post-edit-check.js` |
| Session-start hook | Read-only orientation — prints the pack status + recommended next step when a session starts, so anyone knows what to do. Fail-open; never blocks. | `.claude/hooks/session-start.js` |
| The project's record | `docs/progress/<feature>/progress-and-log.md` — **one file per goal**, planned or fast: a `## Phase N` section of time-stamped lines, a `## Phase N — review` section with the card and proof lines, one `## Review log` table (a row per reviewer run), `## Deferred` findings, `## Field metrics`. If a session ends part-way, `/go` and the startup hook read it to pick the same goal back up. Bookkeeping, never a reviewer finding; proof is the evidence it cites (shape: `implement.md`, *The one record*). | `docs/progress/` (generated, not shipped) |
| Plan-ready check | `node .claude/scripts/plan-ready.js docs/plans/<feature>-master-plan.md` — reads the plan's Plan Review Log and says `READY:` / `NOT READY:` / `UNCHECKED:` (missing file, fail-open). `/implement`, `/start-teams` and `/go` run it before any build. | `.claude/scripts/plan-ready.js` |
| Installation receipt | **What the last install or `/sync-pack` actually observed** — release, timestamp, and a per-file action (copied / skipped-existing / settings-sidecar / customized-merged / missing) with hashes. Optional to a successful install — a missing receipt just means an older install or one that predates this. Never proof that every file is current; `/doctor` check 10 reads it. | `.claude/pack-installation.json` (generated, not shipped) |
| North Star | `NORTH_STAR.md` at the repo root — the one outcome the project exists for. `/create-plan` and `/go` read it to flag scope creep (a Non-goal, or work that doesn't advance the Goal) before code is written. | repo root |
| Runbook | `RUNBOOK.md` at the repo root — the stranger-test operating manual `/bootstrap-claude-pack` writes: deploy, rollback, config inventory (locations, never values), observability, the outside-account inventory (registrar, hosting, payments — where each login lives (never the values) + renewal dates, with a last-reviewed date the critic checks for staleness), and the backup + restore reality check. The `operability-critic` audits it; degrades honestly when a fact is "none found". | repo root |
| Gate rules | `.claude/gate-rules.md` — the one-page canon every gate follows: one run per touched path, frozen tree, severity → action (Medium/Low fixed without re-review; BLOCK/High re-run once), the grade table, one re-run then the person, what a reviewer may not cite, spend in one line, missing-reviewer fallback. | `.claude/gate-rules.md` |
| Reviewer agents | Read-only gate agents (generic + project-specific). `code-reviewer` and `security-reviewer` run on touched Critical Paths; `simplification-reviewer` is an **advisory** over-engineering gate (what to delete/replace with stdlib/native) that judges means not coverage and can never reduce the Definition of Done; `production-reviewer` is an **on-demand** production-readiness gate that runs only when you ask for production quality ("ship to prod", "make this production-ready") or `CLAUDE.md` / `NORTH_STAR.md` declares a production target. **Reviewers judge code and behaviour; docs, tables and counts are never a finding** (`gate-rules.md` §6). | `.claude/agents/` |
| `keeping-it-lean` skill + `/shortcut-ledger` | The leanness canon: the economy-of-means ladder (reuse → stdlib → native → one line) and the `SHORTCUT:` marker convention. `/shortcut-ledger` harvests those markers into a ledger. Economy governs *how* you build, never *how much* you cover. | `.claude/skills/`, `.claude/commands/` |
| `outbound-truth` skill + `outbound-truth-critic` | The outbound-truth canon: every capability claim in something customers read (README claims, changelogs, announcement copy, help docs, privacy claims) traces to shipped code or recorded evidence — an unverifiable claim is a finding; an invented capability forces **Not yet**. `/sync-docs`, `/release`, and `/user-docs` apply it; the critic audits the claims already in the wild via `/audit`. | `.claude/skills/`, `.claude/agents/` |

## The workflow

```
the easy way:       /go <what you want>      (figures out the rest, from any starting point)

drive it yourself:
  new project:      /bootstrap-claude-pack   (once)
  update the pack:  /sync-pack [path-to-claude-pack-repo]  (merge newer improvements without replacing custom work)
  design the UI:    /design <screen or flow>          (choose a direction, build it, and verify the result)
  each feature:     /shape <feature>  →  /create-plan <feature>  →  /implement <feature>  (or /start-teams when a phase needs several specialists)
  small fix:        /shape <fix>  →  fast lane (/implement, no plan docs)  →  report card
  bug report:       /triage <paste the report>  →  reproduce  →  fast-lane fix  →  draft (never send) the reply
  prod is DOWN:     /incident <what's broken>   →  stabilize first (rollback)  →  diagnose  →  fast-lane fix  →  postmortem
  verify a phase:   /review-phase <feature> <N>
  ship a release:   /release            (changelog + migration/env checklist + rollback-before-deploy + smoke test — after the code is Ready)
  keep docs honest: /sync-docs
  docs users read:  /user-docs               (getting-started / how-tos / FAQ — can't overclaim)
  track shortcuts:  /shortcut-ledger [--write]        (show or save deliberate SHORTCUT: markers)
  audit the system: /bootstrap-critics  (once)  →  /audit  (periodically)  ·  /interrogate <file>  (grill one file)
  away for a while: /recap                  (one page: shipped / stuck / decided / heard / the one thing next)
  check the pack:   /doctor                  (Node + configured hooks + engine probes; dispatch evidence and model requests kept separate)
```

`/go` is a convenience over the same machinery, not a shortcut around it: it runs the same
guardrails, reviewer gates, and Definition of Done. It lowers the bar to *start*, never to *ship*.

## How to behave in this project

**Resume from the record.** A session that ends part-way leaves `docs/progress/<feature>/progress-and-log.md` behind; the next `/go` (and the startup hook) reads its last section and `## Review log` and continues from there — nothing is redone, nothing half-done is called done. The installation receipt (`.claude/pack-installation.json`) is separate: `/doctor` check 10 reads it, `/sync-pack` refreshes it, never edit it by hand; a missing receipt is normal for an older install.

1. **Read `CLAUDE.md` and `.claude/project-context.md`** before non-trivial work — they hold this project's golden rules (universal), non-negotiable rules (project-specific), the **Lessons** mistake log (rules distilled from mistakes that actually happened here — obey them; they exist because something already went wrong once), and the Critical-Path → reviewer mapping. They override generic habits.
2. **Follow the gate canon.** Before any reviewer gate, read `.claude/gate-rules.md` and follow it. A change touching N Critical Paths receives N verdicts; reviewers judge code, not paperwork; Medium/Low findings are fixed in the same sitting without re-review; BLOCK/High gets one re-run, then the person decides.
3. **Validation gate before reviewer gates.** typecheck/lint/test must be clean before any reviewer renders a verdict — green, or (when a baseline is recorded at `docs/progress/entry-baseline.md`) no **new** failures vs it; the baseline only ratchets down and retires at green. Give reviewers the exact command and result; the gate re-runs after the fix batch.
4. **If `CLAUDE.md` is missing or thin**, the project isn't set up yet — recommend `/go` (it sets up first, then continues) or `/bootstrap-claude-pack`. The orchestration commands depend on the project contract existing.
5. **If the person seems unsure what to do, point them at `/go`.** They never need to learn the individual command names; `/go` reads the project's state and does the right next thing.
6. **Respect the North Star, and shape before you plan.** If `NORTH_STAR.md` is filled, a feature that hits a Non-goal or doesn't advance the Goal is flagged before planning. For anything vague or ambitious, `/shape` first — make sure you're building the *right* thing — but never inflate a small, clear ask into something bigger; the person decides the scope.
7. **Report gate results as a report card.** Reviewers and `/review-phase` lead with a plain-language readiness line (Ready / Almost / Not yet) earned by the findings, so a non-expert can read the result. The grade follows the findings — a blocker is always "Not yet"; never inflate it.
8. **The guardrail hook is defense in depth.** If it blocks a write, fix the design — don't route around it. If a rule is wrong for this repo, edit `.claude/guardrails.rules.json`, don't disable the engine.
9. **A phase gates on proof, not on a table cell.** A phase is startable only when every phase it *Depends on* is proven complete **on disk** — its `## Phase P — review` section in the record shows `Overall: Ready` above its acceptance proof lines. A `Ready` in the master plan's *Status* column is a *claim*, not the proof; a missing proof defaults to blocked. Planned work requires a READY Plan Review Log (`plan-ready.js`); every build lane and the final review use a separate independent context — a `general-purpose` fallback with the same checklist when a named reviewer is missing, and the generic `code-reviewer` when zero paths are touched. Required docs/config and final affected validation/review precede Ready.
10. **Undo has two layers.** Claude Code natively checkpoints Claude's own file edits on every prompt — `/rewind` restores them, but it does **not** cover what shell commands, codegen, or migrations change. For that wider blast radius, a `Checkpoints: on` line in `CLAUDE.md` (offered once at the first build in a git repo, never assumed) makes the build commands save an **announced** git snapshot before each phase — canonical mechanics in `implement.md` Step 2. Both are safety nets, not a git policy change: nothing is committed, stashed, or dropped without a recorded ask.
11. **Never rely on a spawned agent inheriting your context.** Do not assume session-start orientation, your `CLAUDE.md`, or anything else reaches an agent you spawn. Whether a spawned agent auto-reads `CLAUDE.md` is genuinely unsettled — as of 2026-09-09 the official sub-agents documentation says it does, while the Anthropic blog and issues #62944/#59309 say it does not, with no version boundary either way. The pack does not depend on either reading, because the two are not equally safe: pinning when inheritance works costs some tokens, while trusting inheritance when it doesn't silently strips every convention from every specialist, in a target with nothing to fall back on. So every convention a specialist must honor is pinned **verbatim into its spawn prompt** (`/start-teams` 2b); the phase plan is the single contract. The pin is also the boundary: an implementer reads its own contract, its feature's codebase review and the files it names — never another feature's `docs/plans/*` or `docs/progress/*` unless *Depends on* names them.
12. **Record load-bearing decisions — the decision journal (`DECISIONS.md`).** A team of one has no one to remember *why* a choice was made; six months later the founder is a stranger to their own trade-offs. `DECISIONS.md` at the repo root is that memory — **one line per settled decision**: `- YYYY-MM-DD — <what was decided> — because <why>` (a pointer to the plan/brief when relevant, never a copy of it). This is the **canonical definition** of the convention; the commands below just point here. Two disciplines keep it worth reading, both borrowed from **Lessons**: it is **always offered, never silent** — a person okays every entry — and it is **capped to load-bearing decisions** (a chosen scope, a plan-review trade-off, an accepted risk, an overridden reviewer BLOCK), never every micro-choice. The commands that *make* a decision offer to append at the moment it happens — `/shape` on the chosen scope, `/create-plan` on a settled trade-off, `/go` on an overridden BLOCK or an accepted audit-register risk — and the commands that *plan* (`/shape`, `/create-plan`, `/go`) **read it first when it exists**, so a question settled last month isn't relitigated from scratch — and a request that would *reverse* a load-bearing decision is surfaced for the person to weigh, never silently overturned. The file is **created on first entry** — nothing ships empty, and an absent journal simply means the reading step finds nothing and moves on.

13. **Capture what users ask for — the feedback ledger (`FEEDBACK.md`).** "What should I build next?" is the one-person company's daily decision tax, and the answer lives in what users actually ask for — which is exactly what a solo founder, heads-down building, forgets by next week. `FEEDBACK.md` at the repo root is that memory — **one line per user ask or complaint**: `- YYYY-MM-DD — <what a user asked for / complained about> — <source>` (the source is the *channel* it came from — a support email, a chat, an app-store review — never the person's name, address, or account details). This is the **canonical definition** of the convention; the commands below just point here. Two disciplines, both borrowed from the decision journal above: it is **always offered, never silent** — a person okays every entry — and it is **capped to real user signal** (a genuine ask or complaint from someone using the product), never every idea the founder has in the shower. **Unlike the decision journal, this ledger is a backlog that gets fulfilled** — a decision never closes, but an ask does. So it has one bit of lifecycle: **when an ask ships, mark its line `— done` (or delete it)**, and the "what's next" ranking below reads only the **open** asks (the unmarked lines) — otherwise it would keep re-recommending things already built. (This is also what separates it from **Lessons**: a Lesson asks "how do we not repeat our own mistake?"; feedback asks "what do users want next?" — an outside signal, not our own error.) The commands that might *hear* a user signal offer to append at the moment it surfaces — `/go` and `/shape` when the person mentions an ask they're not building now, `/triage` when a customer report carries a feature request alongside the bug — and the commands that *decide what's next* read it: **`/shape`** reads it as real-job evidence (a request echoing a recurring ask is a stronger signal; related asks reveal the bigger job), and **`/go`'s empty-argument mode** (`/go` with no goal) **ranks the open asks against `NORTH_STAR.md`** — which one most advances the Goal / Current focus — to answer "what should I build next?" with evidence instead of a guess. It **offers** the top pick, never launches a build unasked; with no filled North Star to rank against it lists the asks unranked instead. The file is **created on first entry** — an absent ledger just means the reading step finds nothing and the pack works exactly as before.

## Running on a weaker session model (dials, not a mandate)

The pack works on any model — none of this is a requirement to buy the most expensive tier. These are **dials** that close most of the gap when your session model isn't the strongest the account exposes. The pack concentrates its quality at the gates, so a little asymmetry goes a long way; half of the leverage is operator behavior no command can enforce for you.

1. **Request the strongest model at the gates.** Choose the best model the account exposes for the main session and request it for **every** reviewer gate and critic; the pack's economy permits cheaper implementer requests, never cheaper reviewer requests. Reviewer and critic agents take a `model:` field at the top of each agent file (`.claude/agents/`) — this is a configured request, not proof of the resolved model. The pack also ships every gate agent with **`effort: max`** frontmatter to request maximum effort, while generated implementers default to an **`effort: high`** request to limit over-engineering. Runtime overrides can change the result; actual model and effort remain **unknown** unless exposed by runtime evidence. Two configuration caveats:
   - **By-name only.** The named gate's `effort: max` configuration supplies the request when it is dispatched by name. For a lean merged run or a `general-purpose` fallback (`gate-rules.md` §1, §8) each path reviewer's frontmatter does not carry over: request the strongest available model and include the `"think hard"` brief; session effort settings and that brief are intended effort controls, not evidence of actual runtime effort.
   - **Not retroactive.** A fresh install carries it from the start; an *existing* project gets it only after `/sync-pack` (shipped gates) or a re-bootstrap (generated ones).
2. **Keep Codex** — the pack's independent second-model reviewer — **authenticated** (`.claude/codex-review.md`) so the cross-model check never silently skips. A second model is the cheapest stand-in for a stronger one, and cross-model agreement is the strongest signal the gates produce.
3. **Keep context resumable.** The record (`progress-and-log.md`) holds the goal, scope, evidence and next action. A fresh session is an option, not a mandatory pause: continue authorized whole-goal work unless the person pauses or a real decision is needed.
4. **Request extra thinking at the un-gated judgment moments** — bootstrap's Critical-Path derivation, an ambiguous `/go` route, audit synthesis. These main-loop passes have no reviewer behind them, so one wrong call shapes everything downstream; say **"think hard"** before the step to request more deliberate reasoning. The phrase does not prove the runtime effort setting.
5. **Budget for the one re-run.** More “Almost / Not yet” outcomes are the expected cost of a smaller model, not a sign of failure. `gate-rules.md` §3–§5 say what re-runs and what does not; never trim a gate to save a round.
6. **Set the dial — don't improvise skips.** `Gate intensity: lean` (canon §1) changes how many agents run, never what is checked; use the other dials first when possible, and say on the card when a run was merged.

## Running on a strong session model (the token-economy dials)

The mirror image of the section above: your session model is the strongest tier and **tokens, not model quality, are the constraint**. Together these dials are the pack's **delegation economy** — they aim to cut spend where errors are structurally contained, and never where "done" is decided. One policy generates all of them: **request a cheaper role only when its mistakes cannot ship silently; an upgrade request needs no additional consent; never intentionally request a reviewer below the session model.** Runtime settings can change the result; requested posture is not a runtime guarantee.

1. **Read-only sweeps may request a tier cheaper (this is the canon the commands point to).** The four sweep spawns — `/create-plan` Step 2 (Explore), `/bootstrap-claude-pack` Phase 1 (repo sweep), `/sync-pack` Phase 2 (per-file compares) and its coverage-prospecting sweep — may request a model **one tier cheaper than the session** when the account exposes one (e.g. `sonnet` under an Opus-class session), and **never request a more expensive one**; when the orchestrator can't tell what the account exposes, it requests inherit. Safe by construction: every one of those sweeps returns *conclusions* that are re-verified by the main loop or confirmed by you before anything acts on them, so a weak finding fails loudly instead of shipping — and sweeps are the token-heavy step, so this dial is where most of the potential saving lives.
2. **Implementer economy — consent-only, at bootstrap.** `/bootstrap-claude-pack` Phase 6 offers (never assumes) configuring *generated* implementer agents to request one tier below the session; the default and the recommendation stay **inherit**. Gates, their `model:` consent flow, and their `effort: max` requests are untouched by this dial. Change your mind any time: tell `/go` in plain words ("run builders cheaper" / "stop the economy") and it offers the frontmatter edit with the diff shown; `/doctor` reports the configured posture on request.
3. **Escalation follows demonstrated difficulty.** When a BLOCK/High finding survives its one re-run, the residual goes to the person (canon §5); a stronger builder for the next attempt is a decision they make, not an automatic ladder.
4. **Runtime settings can override these requests.** Check `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_EFFORT_LEVEL` when diagnosing a difference between requested and observed behavior. Exact precedence is *time-sensitive*; verify it against current runtime evidence or documentation. Do not infer resolved model or effort from these settings, a dispatch request, or an agent's frontmatter alone.
5. **Tune the dials on the field metrics, not on model posture.** The record's `## Field metrics` table (reviewer runs, first-pass headline, wall-clock per phase) is the evidence for "did the cheaper tier cost us rounds?". Requested model and effort stay what they are — requests; the pack does not record them on cards.

Two dispatch policies govern these dials: **never intentionally request a reviewer below the session model**, and **never improvise a downgrade** — readers follow the documented cheaper-only rule (unsure → inherit), implementers require recorded consent. These policies describe what the pack requests; actual model and effort remain unknown unless exposed by runtime evidence.
