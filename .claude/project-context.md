## What is being built

Four components on ClientHub (an existing agency platform):

- **C1 Pattern Engine** (Python) — learns what constitutes high-performing UGC per vertical/platform from an external exemplar corpus + closed-loop outcome data. Mines nightly; publishes immutable, content-addressed Pattern Library versions ~quarterly.
- **C2 Scoring & Amplification** (C# control plane + Python extraction) — two gates: Gate A submission approval (deterministic compliance vetoes V1–V6 + LLM-as-judge craft scoring → human verdict), Gate B post-publication amplification recommendation (AWS ranking + budget allocation with reserved exploration).
- **C3 Calibration Monitor** — the referee. Sole authority over the per-cohort circuit breaker (ρ ≥ 0.35, n ≥ 60) and sole veto over *pattern*-library promotion. Has no component doc; spec lives across ADR-0005 and Contracts C/D.
- **C4 Knowledge API** — read-only, holds no tenant data, serves the tenant-neutral `Mechanism` artefact (Contract E). Answers *why*, never *how much*. C2 never calls it; it reads no breaker and writes nothing.

They share five contracts (A–E) and one stateless versioned Extraction Service: two immutable artefacts (Pattern Library → C2, Mechanism Library → C4), one append-only event log (OutcomeEvent, C2 sole writer), one flag (BreakerState), one library verdict. C2 never calls C1 and never calls C4. Everything fails closed. Start at `docs/initial/integration-contract.md`.

## Stack (from tech-spec-ugc-intelligence.md — control/intelligence/frontend planes now built; Hangfire jobs + live LLM still planned)

- **Control plane**: .NET/C# (existing ClientHub API) — identity, tenancy, campaigns, submissions, rights, every deterministic decision. No LLM in any decision path.
- **Intelligence plane**: Python — `yt-dlp`, `ffmpeg`/`ffprobe`, Whisper, scene detection, OCR; `scipy`/`statsmodels` for calibration stats.
- **Jobs**: Hangfire for .NET-side jobs; the nightly trend scan is a Python entrypoint + external cron (ADR-0009). **Frontend**: React/TS manager queue. **Model**: LLM-as-judge, Sonnet-class, schema-constrained output. **Storage**: Postgres-style relational + blob storage (sha256 content-addressed artefacts).

## Phased roadmap (PRD)

0. **Instrument** (2wk) — decision logging + T+24h/48h/7d snapshots on the existing approval workflow. Non-negotiable; nothing user-facing. ← **current focus**
1. **Compliance lane only** (4wk) — deterministic Gate A, no LLM in the decision path. Requires upstream creator-age capture.
2. **Extraction + Pattern Library v0** (6wk). Draft privacy-policy language here.
3. **VPS shadow mode** (6wk) — stored, shown to nobody; graduates only at ρ ≥ 0.35. APP 8 decision required before this phase.
4. **Gate A live, Gate B shadow** (4wk).
5. **Gate B live with exploration active from day one** (4wk).
6. **Mechanism synthesis + Knowledge API** (4wk) — depends on the exemplar corpus (Phase 2) and the trend subsystem, and on **nothing else**: not the scorer, not the breaker, not one outcome event. Could ship before Phase 3; sequenced here for attention, not dependency. Returns empty collections for months by design — `coverage.state` is what distinguishes that from broken.

The two "produce-nothing-user-facing" phases (0 and 3) are explicitly the ones under pressure to be skipped and the ones that determine whether anything is real. Phase 6 has the same shape in a different disguise: the pressure there is to lower `n_trends` to 1 so the API has something to say.
